# Rapport figé rendu par le package en octets HTML sans calcul (`ecrire_rapport()`, module `rapport`) ; rejeu outillé d'une fiche par `rejouer_fiche()` dans `R/construire_table.R`, contrôles avant `construire_table()`, témoins hors de l'objet

*Statut : `proposed`. Rédigé par `architect-approfondi` sur Fable le 24/10/2026 (consultation 1/3 de la branche `claude/rapport-fige`, B8, PR #88 ; Fable d'office au titre de `docs/agents/routage.md`, § 4.1.3, ADR d'architecture ; décision du mainteneur D5, M97), d'après l'avis amont d'`actuary-approfondi` du même jour (statut `complet`, scripts `m1.R` à `m10.R`, mesures sur R1 à R6 à 10⁵ lignes), les issues #86 et #87 (points à fixer, M106) et #77. La décision du mainteneur est attendue **avant tout code de #86 et de #87** (M97). Les questions qui lui reviennent sont réunies en fin d'ADR. Le présent ADR **annote l'ADR 0005** (point 7 (b), « Conséquences » : lieu du rapport figé, écart avec E4.1) et **l'ADR 0011** (troisième annotation du 20/10/2026, (b) : contrat du rejeu outillé ; point 9.4 : module nouveau ; points 3.1 et 8.1 : écrivain unique et octets). Numéros de ligne relevés à `8e66111` ; le nom de l'objet fait foi (convention M77, (b)). Toute mesure marquée « *vérifié* » a été refaite par `architect` sous R 4.3.3, hôte cloud Linux (hors plateforme de référence), `tablexp` installé depuis l'arbre de travail à `8e66111` dans une bibliothèque temporaire (installation sous la locale C : avertissements de traduction de littéraux UTF-8 au chargement, sans effet sur les valeurs mesurées), sur les objets R1 à 10⁵ lignes d'`actuary` (`objets.rds`) ; les mesures reprises de l'avis d'`actuary` sont marquées comme telles.*

## Contexte

**Ce que les textes ont fixé, et où ils divergent.**

1. **E3.5** veut, pour chaque construction, un rapport figé HTML autonome ; **E3.6** en fixe le contenu : restitution **sans recalcul**, empreintes avec leur statut, versions, graine, et la mention que l'empreinte du résultat dépend de la plateforme ; **E3.7** veut qu'un relecteur externe puisse, sans lire le code, savoir ce qui a été calculé et **rejouer** le calcul à partir de la fiche, selon la note de lecture du 19/10/2026 (M64 ; ADR 0011, point 12).
2. **Le lieu du rendu n'est pas le même dans trois textes** (#87) : **E4.1** range dans le module `rapport` les « quantités du rapport, pas son rendu » ; l'**ADR 0005**, « Conséquences », range « fiche, rapport figé, en-têtes de métadonnées » dans le module `rapport` ; **`CLAUDE.md`**, « Architecture », place les « tables HTML » dans `app/affichage.R`. L'**ADR 0004**, point 3, dit que « l'écriture des livrables (Q11) [est] hors moteur : le moteur fournit l'objet et ses métadonnées, l'application les écrit », et son point 2 nomme « l'application, le rapport figé et les tests » comme trois lecteurs distincts de l'objet. L'ADR 0011, point 8.1, a déjà tranché pour la fiche, qui est un livrable de Q11 (ADR 0005, point 7 (c)) : **le package rend des octets, l'appelant écrit le fichier**, et le package n'ouvre aucun fichier (E4.4).
3. **Aucun rejeu outillé n'existe** (#86). `lire_fiche()` ne contrôle pas `version_fiche`, par décision (ADR 0011, troisième annotation du 19/10/2026, (i)) ; le contrôle a été renvoyé à la présente branche (troisième annotation du 20/10/2026, (b) ; M68, C.3), qui doit fixer le motif de refus d'une version inconnue, le contrôle de la représentation et de l'empreinte des données, et la place de la fonction dans le graphe d'appels. Le graphe (ADR 0007, point 2.1 ; `tests/controles/graphe_modules.R:46-58`, `ORDRE_MODULES`, `APPELS_AUTORISES`) interdit à `rapport` d'appeler `R/construire_table.R`, et refuse tout fichier de `R/` hors des modules connus (`:149-152`).
4. **Le rapport figé est le seul livrable qui porte les valeurs exactes.** La fiche ne contient ni exposition ni taux (arbre de `m1.R`, `actuary`) ; les tables CSV et xlsx à en-tête sont reportées à la première branche qui produit une table finale (M93). L'affirmation de #87 « les valeurs exactes restent dans l'objet et dans la fiche » est fausse pour la fiche (`actuary`, § 1.4).

**Vocabulaire de conception** (`codebase-design`). Les deux fonctions décidées ici sont des **adapters** posés devant des modules profonds existants : le rendu devant l'**écrivain unique des valeurs** (`ecrire_valeurs()`, `R/rapport.R:241`, ADR 0011, point 3.1) et l'**empreinte du résultat** (`empreinte_resultat()`, `:443`) ; le rejeu devant le **point d'entrée unique** (`construire_table()`, `R/construire_table.R:210`). Le test de suppression dit où les mettre : supprimer le rendu hors package ferait réapparaître, chez chaque consommateur (application, tests, tiers), une seconde mise en forme des nombres et un second contrôle d'intégrité ; supprimer le rejeu ferait réapparaître ses neuf contrôles chez chaque appelant qui rejoue, ce qui est l'état mesuré aujourd'hui.

## Décision

Proposée par `architect` le 24/10/2026 ; **arrêtée par le mainteneur le … (à compléter)**. Chaque point donne son effet sur les résultats.

### 1. Lieu du rendu : le package, module `rapport`, fichier `R/rapport.R`

1.1. **Le rapport figé est rendu par le package**, dans le module `rapport` (fichier `R/rapport.R`, section délimitée « Rapport figé » en fin de fichier), par une fonction exportée qui rend des **octets** (point 2). Ni `app/affichage.R`, ni une couche hors package. Quatre raisons, dans l'ordre de leur poids :

- **E3.7, rejeu par un tiers.** Un certificateur qui n'a que le package installé (`R CMD INSTALL` n'installe pas `app/`, ADR 0007, « Contexte ») doit pouvoir produire le rapport de son propre rejeu et le rapprocher ligne à ligne de celui qu'on lui remet. Un rendu sous `app/` ou dans une couche hors package le lui interdit.
- **Écrivain unique** (ADR 0011, point 3.1). Le rapport écrit chaque nombre par `ecrire_valeurs(x, "texte")`, fonction interne ; le contrôle d'intégrité (point 2.5) recalcule `empreinte_resultat()`, interne aussi. Rendre hors package obligerait soit à exporter ces deux fonctions et les constantes de statut (`STATUT_EMPREINTE_RESULTAT`, `VERSION_FICHE`, `BLOCS_LECTURE_FICHE`…), ce qui élargit l'interface du package pour un seul appelant, soit à les dupliquer, ce que le point 3.1 interdit.
- **Concordance documentation ↔ moteur** (E3.3 ; `tests/concordance_doc_moteur.R`). Les mentions méthodologiques du rapport — statut de chaque empreinte, légende des quatre statuts, règle des nombres, intervalle binomial « exact » de couverture non établie (`actuary`, § 1.6) — sont du texte du moteur, cité par la documentation et contrôlé par la batterie. Sous `app/`, elles y échapperaient.
- **Frontière calcul / affichage** (E4.3 ; ADR 0004, point 4). Le contrôle d'intégrité et le refus d'une version de fiche non admise sont des contrôles à sens métier : ils vont dans le package quoi qu'il arrive. Le rendu HTML lui-même n'a aucune dépendance à Shiny : le placer sous `app/` ne gagne rien et crée, pour l'application, un second chemin vers les mêmes valeurs.

1.2. **Lecture d'E4.1 (« quantités du rapport, pas son rendu »).** E4.1 fait foi, et deux lectures sont possibles :

- **(a) Note de lecture, sans changement de l'exigence** (recommandée). Le « rendu » qu'E4.1 écarte du module `rapport` est l'**affichage interactif** (les `render*()` de Shiny, les tables HTML de l'écran, les tracés), qui reste dans `app/affichage.R` ; le **rapport figé** est un livrable d'E3.5, construit sur l'objet retourné (ADR 0005, point 7 (b), même jour, même cadrage), que le module `rapport` produit en octets, le fichier étant écrit par l'appelant (ADR 0004, point 3 : « l'application les écrit » ; ADR 0011, point 8.1). Cette lecture rend E4.1, l'ADR 0004 et l'ADR 0005 cohérents entre eux.
- **(b) Amendement d'E4.1** : remplacer « (quantités du rapport, pas son rendu) » par « (quantités du rapport, rendu du rapport figé en octets ; l'affichage interactif est dans `app/affichage.R`) ».

Dans les deux cas le texte est celui du mainteneur (`docs/exigences.md`) : **question 1**. Le présent ADR contredit E4.1 si la lecture (a) est refusée ; il le dit ici explicitement.

1.3. **`CLAUDE.md`, « Architecture »** : la mention « tables HTML » d'`app/affichage.R` désigne l'affichage interactif ; le rapport figé n'y est pas produit. Texte proposé à la session principale (commit `claude:`, après accord du mainteneur, **question 2**) :

- ligne « Package `tablexp` », après « quantités des rapports et empreintes » : ajouter « , rendu du rapport figé (octets HTML, sans calcul ; ADR 0012) » ; après « `R/construire_table.R` (orchestration seule) » : « (orchestration seule, dont le rejeu outillé d'une fiche, `rejouer_fiche()`, qui n'exécute aucune étape ; ADR 0012) » ; après la phrase du point d'entrée unique : « `rejouer_fiche(donnees, fiche)` n'est pas un second point d'entrée : elle contrôle, puis appelle `construire_table()` une fois (ADR 0012, point 3.2). » ;
- ligne « `app/affichage.R` » : « formatage, tables HTML de l'affichage interactif, tracés à partir des quantités du résultat uniquement. Aucun calcul ; le rapport figé n'y est pas construit (package, `ecrire_rapport()`, ADR 0012). »

1.4. **Un seul fichier, pas de module nouveau.** Le rendu va dans `R/rapport.R` et non dans un fichier `R/rapport_fige.R` : « un fichier par module » (ADR 0004, point 1 ; ADR 0007, point 1.2) est contrôlé par `graphe_modules.R` (`:149-152`), et un module nouveau `rendu` placé après `rapport` dans le tableau 2.1 de l'ADR 0007 modifierait un invariant pour **un seul adapter** (le HTML) : « un adapter, c'est un seam hypothétique ». La condition de réouverture, écrite par l'ADR 0011, point 9.4 (« si `rapport.R` devient trop long avec le rapport figé HTML »), est précisée : **le seam devient réel quand un second rendu arrive** — tables CSV et xlsx à en-tête (E3.5, M93) ou rapport figé du suivi d'expérience (Q26) — ; une annotation du présent ADR décidera alors du module `rendu` (après `rapport`, autorisé à appeler tous les modules), avec mise à jour de l'ADR 0007, tableau 2.1, de `graphe_modules.R` et de `CLAUDE.md`. D'ici là, la longueur de `R/rapport.R` (1 126 lignes à `8e66111`) n'est pas un motif de scission.

1.5. **Effet sur les résultats** : aucun. L'empreinte du code change à chaque commit sous `R/`, comparée par jeton (ADR 0009, seconde annotation du 20/10/2026). `app-review` est sans objet pour #87 (aucun fichier sous `app/`) ; le domaine de commit de #87 est `moteur:` + `tests:`.

### 2. Rendu : `ecrire_rapport(x)`, octets UTF-8, déterministe, sans calcul

2.1. **Signature** : `ecrire_rapport(x)`, un seul argument, l'objet de classe `construction` ; rend un vecteur `raw` : octets UTF-8 du document HTML, lignes terminées par LF, LF final, aucun CR, aucune marque d'ordre des octets, comme `ecrire_fiche()` (ADR 0011, point 8.1). L'appelant écrit le fichier (`writeBin`). Le préfixe `ecrire_` suit `ecrire_plan()` et `ecrire_fiche()` : « produire les octets d'un livrable texte », jamais ouvrir un fichier. Aucune option (sections, arrondi, langue) : le rapport minimal a **une** forme ; toute variante serait une seconde définition de la même restitution (Q36 reste ouverte pour la disposition des onglets, pas pour ce document).

2.2. **Aucun calcul** (E3.6 ; ADR 0007, point 6.3 ; critère 2 de #87). Chaque valeur affichée est lue dans l'objet et écrite par l'écrivain unique ; ni somme, ni ratio, ni tri, ni filtrage de cellules ; l'ordre est celui de l'objet. Lire une dimension déjà présente dans les diagnostics ou choisir les lignes du tableau des statuts à citer n'est pas un calcul (`actuary`, § 1.5). Toute quantité nouvelle (totaux, largeur d'intervalle, O/E, comparaison à la loi vraie) se calcule dans le package comme quantité du résultat, change l'objet et l'empreinte du résultat, et relève d'une issue à part (#87, « Hors périmètre »).

2.3. **Règle des nombres : `%.17g` par l'écrivain unique, sans arrondi.** Tout vecteur atomique affiché passe par `ecrire_valeurs(x, "texte")` (`R/rapport.R:241`) : double en `sprintf("%.17g", x + 0)`, jetons `NA`, `NaN`, `Inf`, `-Inf` ; `integer` en `%d` ; `logical` en `TRUE` / `FALSE` / `NA` ; `Date` en ISO 8601 à quatre chiffres ; `character` et `factor` (par ses libellés, type `factor`, comme dans les références, ADR 0009, point 2.3) en UTF-8 **entre guillemets droits avec les cinq échappements**, `NA` sans guillemets ; puis échappement HTML (`<`, `>`, `&`, `"`). Les valeurs du rapport sont donc, caractère pour caractère, celles de la fiche écrite et des `.tsv` de référence : un tiers rapproche les trois sans conversion. **Interdits sur un double** : `format()`, `formatC()`, `prettyNum()`, `as.character()`, `paste()` (mesure du contexte : `OutDec`, `scipen`, `digits` et les 15 chiffres d'`as.character` ; le critère 4 de #87 en dépend). Le document énonce la règle en reprenant la ligne `doubles` de `CONVENTIONS_TEXTE` (« relecture au bit près constatée sous glibc, non garantie ailleurs »). Coût accepté : `niveau` s'affiche `0.94999999999999996` ; une vue arrondie **en plus** relève de Q36 et n'est pas proposée ici (`actuary`, § 1.4).

2.4. **Déterminisme** (E4.6 ; critère 4 de #87). Le document ne porte **aucun horodatage** et ne lit rien dans `execution` ; il porte la mention fixe « ce rapport ne porte pas de date ; la construction est identifiée par ses empreintes ». Deux constructions identiques hors `execution` donnent les mêmes octets ; les octets sont identiques sous `LC_ALL=C` et `C.UTF-8` (littéraux du moteur par `texte_moteur()`, `R/outils.R:131`, #50, #81) et quelles que soient `OutDec`, `scipen`, `digits`. Un rapport se compare donc par son MD5.

2.5. **Contrôle d'intégrité avant le rendu** (recommandation d'`actuary`, § 1.7, retenue). Dans cet ordre, chaque refus par `refuser("rapport", …)` :
1. `x` n'est pas de classe `construction` : `rapport_objet_invalide` (un refus nommé, non une erreur de programmation : la fonction est exportée et reçoit l'objet de l'appelant) ;
2. `x$fiche$version_fiche` n'est pas `identical` à `VERSION_FICHE` : `version_fiche_non_admise`, **même motif que le rejeu** (point 3.5) — les chemins des sections dépendent de la version ; un objet d'une autre version ne peut venir que d'un `readRDS()` d'un code antérieur ;
3. `empreinte_resultat(x)` différente de `x$fiche$empreintes$resultat` : `objet_modifie` (« objet modifié après sa construction : empreinte du résultat recalculée {a} au lieu de {b} »). Ce recalcul est celui d'un **contrôle**, pas d'une quantité affichée ; il réécrit les bits de l'objet (forme « empreinte », exacte par construction) et non le calcul : il est portable, un objet sauvegardé puis rechargé passe (*vérifié*). Coût : 0,51 s à 10⁵ lignes (*vérifié*).

2.6. **Mentions « non produit » lues dans l'objet, jamais dans une liste figée du rendu seul** (`actuary`, § 1.3). Le rendu porte une liste fermée de sections `SECTIONS_RAPPORT` (constante de `R/rapport.R`), chaque section liée à ses chemins dans l'objet et à sa règle de présence, lue dans l'objet : `table` vaut `NULL` → « table finale : non produite par cette version » ; `validation` absent de `names(etapes)` → « validations : non produites par cette version » ; `exposition` absent de `names(etapes)` → « non demandée par le plan ». La distinction entre « non demandée par le plan » (étape du catalogue absente du plan) et « non produite par cette version » (aucune fonction d'étape) ne peut pas se lire dans l'objet : elle vient de la liste, et un **test de la batterie** (contrôle mécanique, principe 7 des workflows) vérifie que les sections marquées « étape du catalogue » sont exactement `ETAPES$etape` (`R/construire_table.R:37`, lue par `tablexp:::` dans le test) et que les sections « non produites » ne correspondent à aucune étape du catalogue. Le jour où une étape `validation` existera, la batterie échouera tant que le rendu n'aura pas de section pour elle : rien ne reste « non produit » par oubli. Aucune section « écarts » aux notes II1291 tant que M90 (c) n'est pas tranchée (M103).

2.7. **Forme du document** (le contenu section par section est fixé par la spécification d'`actuary`, qui part de son avis, § 1.1 à 1.6) : un seul fichier HTML, `<meta charset="utf-8">`, feuille de style **en ligne** admise (ce n'est pas une ressource externe), ni `<link>`, ni `<script>`, ni `<img>` (tracés reportés : R de base n'a pas d'encodeur base64, *vérifié*, #87), ni police externe ; un test par motif le vérifie. Chaque section cite le **chemin** de ses quantités dans la grammaire des références et de la fiche (`etapes/brut/resultat/poisson`, `fiche/empreintes/donnees`…). Deux primitives de présentation suffisent : une **table de colonnes** pour un `data.frame` (une colonne par colonne, valeurs par l'écrivain) et une **table de lignes** `chemin | type | longueur | valeurs` pour tout autre sous-objet (plan, paramètres, diagnostics), qui est l'aplatissement de la grammaire 1 présenté en HTML : mêmes chemins que la fiche et les `.tsv`. Le tableau `etapes/brut/parametres/statuts` s'affiche **en entier et tel quel** avant les tableaux de résultats, avec la légende sur l'intervalle binomial « exact » (`actuary`, § 1.6) ; les tables de lignes non bornées (`lignes_conservees`, `observations`, `numeros_conserves`, `lignes_exclues`, `kaplan_meier_sauts`) ne sont **pas** reproduites, leur chemin et leur dimension (lue dans les diagnostics) sont cités. Mentions obligatoires : statut de chaque empreinte (données : portable, exacte sous glibc, non mesurée ailleurs ; fichier : calculée par la couche de lecture, **non vérifiée par le moteur** ; résultat et code : `statut_resultat_code` ; MD5 sans rôle de sécurité) ; la phrase fixe « L'empreinte du résultat dépend de la plateforme (R, BLAS, LAPACK, bibliothèque C) ; elle n'est un témoin d'identité que sur la même machine (E3.6, E4.6) » ; `graine_mention` à côté de `graine` ; la section « Rejeu », qui reprend la ligne `# rejeu` de la fiche et nomme `rejouer_fiche()` ; les noms de `fiche$plateforme` lus dans l'objet, pour que le champ de #77 apparaisse sans retouche.

2.8. **Export** : `ecrire_rapport` dans `NAMESPACE`, motivé par ses appelants hors package (application, tests, tiers), cité dans `docs/latex/` par `docwriter` ou inscrit dans `tests/concordance_attente.csv` avec renvoi à #87 d'ici là (ADR 0007, point 3.4).

2.9. **Effet sur les résultats** : aucun (le rendu lit l'objet sans le modifier ; objet, fiche et références inchangés). Taille du document et durée du rendu sur R1 à R6 : constat de mesure consigné dans le commit, sans seuil (critère 7 de #87).

### 3. Rejeu outillé : `rejouer_fiche(donnees, fiche)` dans `R/construire_table.R`

3.1. **Signature et retour.** `rejouer_fiche(donnees, fiche)` : `donnees`, un `data.frame` (jamais un fichier, E4.4) ; `fiche`, la liste de la fiche, relue des octets de son texte par `lire_fiche()` chez l'appelant (ADR 0011, point 8.1) ou prise dans `x$fiche`. Les rôles, le plan et la provenance **viennent de la fiche** ; la fonction n'en reçoit pas d'autres. Elle rend une liste nommée de classe S3 **`rejeu`** à deux éléments : `construction`, l'objet rendu par `construire_table()`, **sans aucune modification ni attribut** (il reste `identical` hors `execution` à un original ; le périmètre de l'empreinte du résultat n'est pas touché) ; `bilan`, un `data.frame` à cinq colonnes `character` — `controle`, `attendu`, `lu`, `verdict`, `statut` — une ligne par contrôle, **ceux qui passent compris**, puis une ligne par témoin (3.6). La classe `rejeu` sert au contrôle d'entrée par `inherits()` d'un consommateur futur, comme `construction` (ADR 0007, point 6.1) ; le bilan **n'entre pas dans l'objet** (`actuary`, § 2.6) : c'est la trace du rejeu pour E3.7, puisque l'objet rendu ne se distingue pas d'un original.

3.2. **Lecture du point d'entrée unique** (ADR 0004, point 2 ; `CLAUDE.md`, « Architecture »). `construire_table()` reste la **seule fonction qui exécute un plan**. `rejouer_fiche()` n'exécute aucune étape, n'appelle aucune fonction d'étape, ne calcule rien d'autre que ses contrôles (dont l'empreinte des données, par `empreinte_donnees()` du module `rapport`) et ses témoins (comparaisons de chaînes) ; elle appelle `construire_table()` **exactement une fois**, avec `fiche$roles`, `fiche$plan` et `fiche$provenance`, et ne touche pas à sa signature. Ce n'est donc pas un second point d'entrée de la construction, mais un **adapter** devant lui : le relecteur qui part de `rejouer_fiche()` descend dans `construire_table()` (ADR 0004, point 6 (a)). L'invariant se lit désormais : « point d'entrée unique de la construction ; toute fonction exportée qui construit l'appelle, sans exécuter d'étape elle-même ». Un test montre que, sur un refus du rejeu, `construire_table()` n'est pas appelée (critère 3 de #86).

3.3. **Fichier et graphe d'appels** : `R/construire_table.R`, fichier d'orchestration (ADR 0007, point 3.1), seul fichier autorisé à appeler à la fois `valider_plan()`, les contrôles des modules et `construire_table()` (`APPELS_AUTORISES$construire_table` = tous les modules, `graphe_modules.R:57`) ; `rapport` ne peut pas appeler `construire_table()` (point 2.1). Un troisième fichier transversal `R/rejouer.R` est écarté : il modifierait l'ADR 0007, point 1.2, `CLAUDE.md` et `MODULES` de `graphe_modules.R` pour une fonction de quelques dizaines de lignes. « Aucun calcul » dans ce fichier reste vrai : les contrôles délèguent aux modules.

3.4. **Ordre des contrôles** (`actuary`, § 2.1, retenu). Le rejeu s'arrête au premier refus ; `construire_table()` n'est jamais appelée si un contrôle échoue :
1. **nature des arguments** : `fiche` est une liste et non un objet `construction` (sinon le message dit « passer `x$fiche` ») ; `donnees` est un `data.frame` ;
2. **forme des champs que le rejeu lit lui-même**, motif `fiche_non_conforme` (champ, forme lue, forme attendue) : `version_fiche` entier de longueur 1, non `NA`, sans attribut (forme exacte, #21 ; un `double` 3 relu d'un texte édité est refusé) ; `empreintes` liste nommée portant `algorithme`, `representation`, `donnees`, chacun chaîne unique non `NA` ; noms `roles`, `plan`, `provenance` présents (`provenance` peut valoir `NULL`, nom présent) ; le contenu de `roles`, `plan` et `provenance` est laissé à l'étape 6 ;
3. **`version_fiche` admise** (3.5), avant tout le reste : la version donne le sens des autres champs ;
4. **`empreintes$algorithme`** égal à `ALGORITHME_EMPREINTE` (`md5`) : sinon `algorithme_empreinte_inconnu` ;
5. **`empreintes$representation`** égale à `ENTETE_CANONIQUE` : sinon `representation_non_admise` (le recalcul se ferait sous une autre définition et échouerait toujours, avec un motif trompeur) ;
6. **contrôles d'entrée de `construire_table()`**, avec leurs motifs propres et dans son ordre (`R/construire_table.R:215-221`) : `valider_plan(fiche$plan)`, `controler_roles(donnees, fiche$roles, plan$segmentation)`, `controler_provenance(fiche$provenance)`. Motif : sans eux, une colonne de rôle absente donnerait `type_non_canonique` et une date en `character` une « empreinte discordante » (mesures du contexte) ; le refus doit nommer la cause la plus précise. Coût 0,025 s (*vérifié*) ; ils sont refaits par `construire_table()`, sans dommage ;
7. **empreinte des données recalculée** par `empreinte_donnees(donnees, fiche$roles)` et comparée à `fiche$empreintes$donnees` : sinon `empreinte_donnees_discordante` ;
8. **`construire_table(donnees, fiche$roles, fiche$plan, fiche$provenance)`** ;
9. **témoins** (3.6), jamais motifs de refus.

3.5. **Versions admises : la version courante seule.** Constante `VERSIONS_FICHE_REJEU` (vecteur d'entiers, valeur initiale `VERSION_FICHE`, soit 4 après #77 si l'incrément est retenu ; placée dans `R/rapport.R` à côté de `VERSION_FICHE`, parce qu'une constante de premier niveau de `R/construire_table.R` ne peut pas lire `rapport.R`, évalué après lui — ADR 0011, quatrième annotation du 20/10/2026, (c) 3 — ; `rejouer_fiche()` la lit à l'appel). Motifs : aucune migration silencieuse (ADR 0011, point 10 (d)) ; une fiche d'une autre version donne par construction un témoin « différente », même sur la même machine (`version_fiche` est empreintée) ; aucune fiche d'une version antérieure n'a été livrée hors des tests. Élargir demandera, version par version, de montrer par une annotation que les champs lus par le rejeu ont la même structure et le même sens. Motif de refus `version_fiche_non_admise`, dont le message cite la version lue, les versions admises, `fiche$versions$tablexp` **et `fiche$empreintes$code`** (la version du package vaut `0.0.0.9000` depuis `1d49e17` et ne permet pas de retrouver le code ; `actuary`, § 2.2, issue proposée), l'empreinte du code installé, et « aucune conversion de fiche n'est faite ».

3.6. **Témoins, hors de l'objet, jamais motifs de refus** (point 11.2 de l'ADR 0011 ; E3.6, E4.6). Lignes du bilan, après les contrôles :
- **code** : `fiche$empreintes$code` comparée à `EMPREINTE_CODE` (`R/rapport.R:491`) ; verdict « identique », « différent » ou « non déterminable » (`NA` d'un côté ou de l'autre, sources introuvables). Rejouer une fiche avec un code corrigé est un usage légitime (analyse de sensibilité du certificateur) : un écart est signalé, pas refusé ;
- **R** et **plateforme** : `fiche$versions` et `fiche$plateforme`, champ par champ, **noms lus dans la fiche** et dans l'objet rendu (le champ de #77 y entre sans retouche) ; verdict « identiques » ou la liste des champs qui diffèrent ;
- **fiche** : la fiche rendue comparée à la fiche reçue, hors `versions`, `plateforme`, `empreintes$resultat`, `empreintes$code` et `empreintes$statut_resultat_code` (`identical`) ; verdict « identique » ou la liste des champs qui diffèrent. Ce témoin distingue un code au comportement différent (recette, convention, fin effective, hypothèses, décomptes d'exclusion, avertissements) d'un écart numérique de dernier bit ; il ne coûte qu'une comparaison. Ajout d'`architect`, à confirmer par la spécification d'`actuary` ;
- **empreinte du résultat** : `construction$fiche$empreintes$resultat` comparée à `fiche$empreintes$resultat` ; verdict « identique », « différente » ou « non déterminable » ; statut « témoin, même machine seulement ». Une empreinte « différente » quand code, R, plateforme et fiche sont identiques est un **signal d'écart à E4.6** ; sinon c'est un écart possible attendu (R4 et R5 entre la CI et l'hôte cloud), et le critère de rejeu est la comparaison à tolérance par classes, hors du rejeu outillé (ADR 0011, point 12 (3)) ;
- **empreinte du fichier** : « reprise de la fiche, non vérifiée par le moteur » (recopiée par `provenance`, mesure G d'`actuary`).

Statuts de la colonne `statut` : « exacte ; sans rôle de sécurité » pour les égalités MD5 (contrôles 4, 5, 7 ; témoin code) ; « témoin, même machine seulement » pour l'empreinte du résultat ; « comparaison exacte » pour les autres. Les libellés exacts sont fixés par `coder` et validés par `actuary`.

3.7. **Moment de l'empreinte des données : avant `construire_table()`, après les contrôles d'entrée** (étapes 6 et 7). Coût : l'empreinte est calculée deux fois par rejeu (une fois par le rejeu, une fois par `construire_table()`, qui ne reçoit pas d'empreinte : changer sa signature toucherait un contrat partagé, § 4.2, pour économiser 15 %), soit +14 à +20 % de temps à 10⁵ et 10⁶ lignes, **sans relever le pic de mémoire** du rejeu (`actuary`, `m4.R`) ; sur des données discordantes, le refus tombe avant la construction et économise environ 85 % du temps. L'ordre reste celui de `construire_table()` : « validation entière avant toute exécution » (`R/construire_table.R:212`). 10⁷ lignes n'est pas mesuré (#83, M101).

3.8. **Module déclaré des refus** : `construire_table`, comme les refus de `valider_plan()` (`R/construire_table.R:89`), pour les cinq motifs propres au rejeu (`fiche_non_conforme`, `version_fiche_non_admise`, `algorithme_empreinte_inconnu`, `representation_non_admise`, `empreinte_donnees_discordante`) ; les refus délégués gardent leur module (`donnees`, `rapport`, `construire_table`). Textes des motifs : proposition d'`actuary`, § 2.5, reprise par sa spécification ; chaque message cite la valeur lue et la valeur attendue ; celui de l'empreinte des données rappelle le périmètre (colonnes des rôles de la fiche, lignes dans l'ordre reçu ; « un autre ordre des lignes, une valeur ou un type de colonne différents suffisent à la changer ; les colonnes hors rôles n'y entrent pas »).

3.9. **Cas adverses à constater et tester** (critère 6 de #86 ; `actuary`, § 2.7) : lignes permutées → refus justifié (exposition et taux non `identical`, 3,0e-15) ; colonne hors rôle ajoutée ou retirée → passe, témoin « identique », objet non `identical` sur `lignes_conservees` (hors périmètre, M71 : le critère 4 de #86 ne vaut que sur les mêmes colonnes, à documenter) ; colonne de rôle renommée avec rôles adaptés → passe ; plan de la fiche modifié (`niveau` 0,99) → passe, témoin « différente » sur la même machine, indétectable ailleurs (la fiche ne porte pas d'empreinte d'elle-même : voulu) ; fiche sans puis avec provenance → se rejouent, empreintes du résultat distinctes entre elles (`fiche$provenance` est dans le périmètre) ; `version_fiche` en double → `fiche_non_conforme` ; version 3 après #77 → `version_fiche_non_admise` ; empreinte du résultat ou du code à `NA` → « non déterminable » ; R1 à R6 écrites, relues, rejouées → `identical` hors `execution`, témoin « identique » (critère 4).

3.10. **Export** : `rejouer_fiche` dans `NAMESPACE`, motivé par ses appelants hors package (tests, tiers, application plus tard) ; cité dans `docs/latex/` ou inscrit dans `tests/concordance_attente.csv` avec renvoi à #86 (ADR 0007, point 3.4). Contrat partagé touché : nouvel export et sa signature (§ 4.2) ; la signature de `construire_table()` est inchangée.

3.11. **Effet sur les résultats** : aucun. Fonction nouvelle ; `construire_table()`, la fiche, `VERSION_FICHE` et les références ne changent pas.

## Options écartées

- **Rendu sous `app/affichage.R`** (lecture littérale de `CLAUDE.md`, « tables HTML ») : indisponible à un tiers qui n'a que le package ; exports d'internes ou duplication de l'écrivain et de l'empreinte ; mentions méthodologiques hors concordance ; dépendance de fait du livrable d'E3.5 à l'existence d'un dossier qui n'existe pas encore ; `app-review` requis pour un document qui n'a rien de Shiny.
- **Couche mince hors package sans Shiny** (fichier sous `app/` ou script sous `inst/`) : mêmes défauts que ci-dessus, moins la dépendance à Shiny ; `R CMD INSTALL` n'installe pas `app/` et un script sous `inst/` lu par `system.file()` à l'exécution réintroduit une lecture de fichier par le package ; aucun gain mesurable, puisque le rendu n'a pas de dépendance à écarter du moteur.
- **Module nouveau `rendu` dès maintenant** : un seul adapter, seam hypothétique ; modifie l'ADR 0007, tableau 2.1, `graphe_modules.R` et `CLAUDE.md` ; à rouvrir au second rendu (point 1.4).
- **Fichier `R/rapport_fige.R` dans le module `rapport`** : « un fichier par module » est contrôlé par script ; admettre un module sur deux fichiers changerait l'ADR 0007, point 1.2, pour la seule commodité de lecture.
- **Nombres arrondis dans le rapport** (chiffres significatifs) : le rapport est le seul livrable qui porte les valeurs exactes (contexte, 4) ; un certificateur ne recalcule D / E^c et les bornes `qgamma`, `qbeta` au bit près qu'avec `%.17g` ; six chiffres ne vérifient qu'à 10⁻⁶, très au-dessus des classes 1e-12 et 1e-14 avec lesquelles un rejeu se compare ; une seconde mise en forme des nombres serait une seconde définition (ADR 0011, point 3.1). La vue arrondie, si elle est voulue, s'ajoute (Q36), elle ne remplace pas.
- **Chaînes sans guillemets dans le rapport** : plus lisible, mais `NA` et `"NA"` se confondraient, et le rapport cesserait d'être, caractère pour caractère, la fiche et les `.tsv`.
- **Horodatage dans le document** (« généré le … ») : interdit par E4.6 et par le critère 4 de #87 ; l'identité du document est celle de ses empreintes.
- **Rendu sans contrôle d'intégrité** : un objet altéré avant le rendu afficherait des valeurs altérées sous l'empreinte d'origine (`actuary`, § 1.7) ; 0,51 s à 10⁵ lignes contre un rapport qui ment.
- **Rendu qui admet toute `version_fiche`** : les chemins des sections dépendent de la version ; même règle que le rejeu.
- **Bilan du rejeu dans l'objet** (champ ou attribut) : l'objet ne serait plus `identical` à un original, le périmètre de l'empreinte du résultat changerait, et `empreinte_resultat()` refuse tout attribut inconnu (erreur de programmation, M71).
- **Rejeu qui rend l'objet seul** : la trace du rejeu (E3.7) serait perdue, et chaque appelant recomparerait les empreintes à sa manière.
- **Rejeu dans le module `rapport`** : interdit par le graphe (ne peut pas appeler `construire_table()`) ; l'autoriser créerait un cycle `rapport` ↔ `construire_table.R`.
- **Rejeu avec arguments `roles`, `plan`, `provenance`** de l'appelant : rejouerait autre chose que la fiche ; c'est `construire_table()`.
- **Écart d'empreinte du code en refus** : interdirait l'analyse de sensibilité sur code corrigé ; le témoin suffit (`architect`, avis préliminaire de #86, confirmé par `actuary`).
- **Versions antérieures admises au rejeu** (fiche 3 après #77) : témoin « différente » par construction, et la correspondance structure ↔ version devrait être prouvée pour chaque version admise ; aucune fiche antérieure livrée.
- **Empreinte des données après `construire_table()`** (un seul calcul) : le refus tomberait après 85 % du travail, et les mesures montrent que le calcul préalable ne relève pas le pic de mémoire.
- **Empreinte des données avant les contrôles d'entrée** : motifs trompeurs mesurés (`type_non_canonique`, « empreinte discordante » au lieu de `colonne_absente`, `type_incompatible`).
- **Transmettre l'empreinte calculée à `construire_table()`** pour éviter le double calcul : change la signature du point d'entrée (contrat partagé) pour 15 % de temps.
- **Numéros des lignes exclues dans le rapport** : volume non borné ; les « premiers numéros » seraient une troncature à déclarer (Q36) ; le chemin est cité.
