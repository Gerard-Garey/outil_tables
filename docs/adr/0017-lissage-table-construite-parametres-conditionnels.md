### 1. Contrat commun de la « table construite » (F1)

1.1. **Définition.** La *table construite* d'une construction est la table de taux annuels de décès produite par l'**étape productrice** du plan (dans B19 : `lissage` ou `positionnement`), sur la plage d'âges de cette étape. Elle n'est **pas** `x$table` (table finale de l'ADR 0007, point 6.1, `NULL` jusqu'à l'étape `table`) ; elle vit dans le `resultat` de l'étape productrice (ADR 0015, point 5.2). Au sens du visa (`CLAUDE.md`, « Changements de résultats »), un changement de table construite est soumis au mainteneur comme un changement de table finale (précédent M308 pour la table positionnée ; P4 du § 1.20).

1.2. **Colonnes communes**, que lisent tous les lecteurs et eux seuls : les clés de segmentation du plan (dans l'ordre du champ `segmentation`), `age` (`integer`), `qx` (`double`, fini, dans [0, 1]), `etat` (`character`). Lignes : la grille complète segments × âges de la plage, segments dans l'ordre de la table d'exposition, âges croissants ; aucune colonne `annee` (les deux producteurs refusent ou ignorent `par_annee`, I-L1 et `table_positionnee`) ; `data.frame` nu, sans attribut de métadonnées. Chaque producteur ajoute librement **après** ces colonnes les siennes (`qx_reference` et bornes du positionnement ; bornes de crédibilité de (b), D6) ; aucun lecteur ne les lit par le contrat. *Voir l'annotation du 11/11/2026, point 5.5.*

1.3. **Une seule grandeur stockée, `qx`.** La force se lit par la règle unique du moteur, μ = −log1p(−q) (force constante par âge entier ; `PORTEE_PROBABILITE$dernier_anniversaire`, `R/brut.R`), qu'appliquent déjà `attendus_cellules()` et la validation. Aucune colonne `mu` : deux colonnes liées par une identité seraient deux sources qui peuvent diverger. Sous (b), qui calcule μ̂ nativement, `qx = −expm1(−μ̂)` et le lecteur retrouve μ̂ à l'aller-retour près (quelques unités de dernier rang ; I-L3) ; l'état `qx_arrondi_un` signale q = 1 par arrondi, comme au positionnement. Aucune fonction d'enveloppe n'est créée pour cette expression d'une ligne (test de suppression : elle ne concentrerait aucune complexité).

1.4. **États.** `etat` porte un vocabulaire propre à chaque producteur (`ETATS_TABLE_POSITIONNEE` : `produite`, `taux_table_nul`, `taux_table_egal_un`, `qx_arrondi_un` ; lissage, indicatif : `observee`, `interpolee`, `qx_arrondi_un`). Le contrat n'impose pas de vocabulaire commun ; un lecteur qui écarte des états (la fermeture, `interpolee`, point 7) les nomme dans sa spécification et refuse un état inconnu par une erreur de programmation. Option écartée : vocabulaire commun obligatoire, qui ferait changer `table_positionnee` (R10) sans besoin.

1.5. **Sélection par propriété dans `ETAPES`.** `ETAPES` gagne une colonne `table_construite` (`character`) : le nom de l'élément du `resultat` qui porte la table construite (`"table_lissee"` pour `lissage`, `"table_positionnee"` pour `positionnement`), `NA` pour les autres étapes. L'orchestration (`construire_table()`) lit cette colonne, prend la table de l'étape productrice exécutée, contrôle le contrat 1.2 (erreur de programmation si la table ne le tient pas ; fonction indicative `table_construite()` dans `R/construire_table.R`) et la passe aux lecteurs **en valeur** (argument `table_construite`), comme elle passe aujourd'hui `etapes[["positionnement"]]` à la validation. Aucun lecteur ne connaît le nom de l'étape productrice.

*Complément du 11/11/2026 (relecture d'`actuary`).* « Aucun lecteur ne connaît le nom de l'étape productrice » vaut pour la **table elle-même** (sa sélection, son contrôle, sa lecture). Il ne vaut pas pour la **cohérence entre une relation de validation et son producteur** : sous `positionnee`, la validation exige l'étape `positionnement` au plan et la même plage (`positionnement_absent`, `plage_ages_differente_positionnement`, `R/validation.R:555`, `:560` à `263bc42`) ; sous `lissee`, de même l'étape `lissage` (`lissage_absent`, `plage_ages_differente_lissage`, point 15). Ces contrôles nomment le producteur attendu par la relation, à dessein : la relation est une déclaration sur la table validée.

1.6. **Options écartées.** (a) *Branchement des lecteurs sur `etapes$lissage` ou `etapes$positionnement`* : chaque producteur nouveau toucherait chaque lecteur ; le test de suppression le condamne. (b) *Ranger la table construite dans `x$table`* : contredit l'ADR 0007, point 6.1, et l'ADR 0015, point 5.1 ; la table finale suppose la fermeture et l'étape `table`. (c) *Contrôle du contrat dans un module bas (`lissage`, `brut`)* : obligerait `positionnement` à appeler un module pour une constante, ou mettrait du contenu métier dans `outils` ; l'interface entre étapes relève de l'orchestration, où vivent déjà `ETAPES` et `PARAMETRES_ETAPES`. (d) *Faire passer la validation `positionnee` par la table construite* : elle lit θ̂ à dessein (attendus finis même si `qx` vaut 1 par arrondi) ; R8 à R13 resteraient identiques en valeur mais le chemin changerait sans gain.

1.7. **Effet sur les résultats** : aucun pour R1 à R14 (colonne de constante ; aucun plan existant n'a de lecteur nouveau).

### 2. Place de `lissage` dans `ETAPES` ; une seule étape productrice par plan (F2, D9)

2.1. **Rang.** `lissage` entre dans `ETAPES` après `brut` et avant `positionnement` (ordre des modules), module `lissage`, fonction indicative `calculer_lissage()`, préalables `c("donnees", "exposition", "brut")`, `aleatoire = FALSE`.

2.2. **D9 par propriété.** `valider_plan()` refuse un plan qui contient plus d'une étape dont `ETAPES$table_construite` n'est pas `NA` (motif indicatif `tables_construites_multiples`, module `construire_table`, message qui nomme les étapes). La règle est écrite une fois et vaut pour tout producteur futur ; elle reprend la lettre de l'ADR 0007, point 5.1 (« `lissage` ou `positionnement` »).

2.3. **Méthode 4** (lissage de la table du moment avec dérive de la référence, E2.12) : ce sera une méthode d'une seule étape productrice (valeur de `methode` de `lissage` ou de `positionnement`, à fixer par sa spécification), non une combinaison de deux étapes ; la règle 2.2 tient. La table finale (`x$table`) sera désignée par l'étape `table` à partir de la table construite, fermée ou non (hors du présent ADR).

2.4. **Options écartées.** (a) *Refus écrit sur les deux noms* (`lissage` et `positionnement`) : à réécrire pour chaque producteur. (b) *Admettre les deux et désigner la table construite par un paramètre* : D9 l'exclut ; aucune lecture actuarielle ne combine aujourd'hui une table lissée et une table positionnée dans une construction.

2.5. **Effet sur les résultats** : aucun (R10, seul plan à `positionnement`, n'a pas de lissage) ; messages des refus `etape_inconnue` et `etapes_hors_ordre`, qui listent `ETAPES$etape`, changent (refus, visa d'`actuary`).

### 3. Paramètre conditionnel à la valeur d'un paramètre gouvernant de la même étape (F3, F13)

3.1. **Besoin.** I-L1 et I-L2 partagent une étape dont les paramètres dépendent de la variante ; la validation `lissee` ne lit aucune table de référence (F13). La colonne `recette` de `PARAMETRES_ETAPES` ne connaît que la recette, déduite des rôles.

3.2. **Mécanisme.** `PARAMETRES_ETAPES` gagne deux colonnes : `selon` (`character` : nom d'un paramètre **gouvernant** de la même étape, ou `NA`) et `valeurs` (colonne liste : valeurs du gouvernant sous lesquelles le paramètre est requis). Règles, citables :
- un paramètre porte **au plus une** condition : `recette` ou `selon` ;
- le gouvernant est un paramètre **sans condition**, de type `character`, chaîne unique (profondeur 1, aucune chaîne de conditions ; invariant testé sur le catalogue) ;
- `valider_plan()` contrôle d'abord la forme et le domaine du gouvernant (fonction de contrôle du module), puis la présence des paramètres qui en dépendent — absent sous une valeur qui l'exige : `parametre_manquant` ; présent sous une autre : `parametre_inattendu` (motifs existants, module `construire_table`, message qui nomme le gouvernant et sa valeur) —, puis leurs valeurs ; la condition sur la valeur d'un paramètre ne dépend pas des rôles, elle est donc contrôlée **dès `valider_plan()`**, à la différence de la condition sur la recette ;
- *complément du 11/11/2026 (relecture d'`actuary`)* : un **contrôle croisé entre deux gouvernants** de la même étape (dans B19 : `critere_lissage` × `methode`, point 3.4) appartient au contrôle de forme et de domaine des gouvernants ; il **précède** le contrôle de présence des paramètres qui en dépendent. Un plan dont un gouvernant est hors de son domaine, seul ou croisé avec un autre, est refusé par ce motif de domaine, jamais par `parametre_manquant` ou `parametre_inattendu` ;
- `canoniser_plan()` : la règle « noms inclus dans le catalogue de l'étape et contenant tous les paramètres sans recette » (ADR 0016, point 7.2) devient « … contenant tous les paramètres **sans condition** » ; ordre du catalogue restreint aux présents.

3.3. **Règle générale, citable** (étend la règle 7.3 de l'ADR 0016) : *un paramètre d'étape est requis quand sa condition est remplie et interdit sinon ; la condition porte sur la recette retenue (colonne `recette`) ou sur la valeur d'un paramètre gouvernant de la même étape (colonnes `selon`, `valeurs`) ; un paramètre sans condition est requis sous tous les plans.* Aucun défaut implicite n'est créé (ADR 0005, point 3).

3.4. **Application dans B19** (noms et valeurs indicatifs, fixés par `coder` sur les spécifications ; motifs visés par `actuary`) :

| Étape | Paramètre | Condition |
|---|---|---|
| `lissage` | `methode` (`wh_quadratique` pour (a), `wh_poisson` pour (b)), `plage_ages`, `ordre_difference`, `critere_lissage` (`declare` ou `laml`) | aucune (requis) |
| `lissage` | `ponderation` (`uniforme`, `exposition` ; D2) | `selon = methode`, `valeurs = wh_quadratique` |
| `lissage` | `niveau` (intervalles de crédibilité, D6) | `selon = methode`, `valeurs = wh_poisson` |
| `lissage` | `parametre_lissage` (h ou λ déclaré) | `selon = critere_lissage`, `valeurs = declare` |
| `lissage` | `intervalle_lissage` (bornes de λ) | `selon = critere_lissage`, `valeurs = laml` |

`critere_lissage = "laml"` sous (a) est un refus de domaine (D3 ; fonction de contrôle du module, comme `binomial` sous `par_annee`), non une condition. **Écart de forme à la spécification de #225**, qui écrivait « soit `parametre_lissage`, soit `critere = "laml"` avec `intervalle_lissage` » : une présence alternative est une disjonction que le mécanisme n'admet pas ; le choix est rendu explicite par `critere_lissage`, sans défaut, aussi sous (a) (`declare`). Fond inchangé ; à viser par `actuary`.

*Complément du 11/11/2026 (relecture d'`actuary`, Q2 visée).* L'écart de forme est visé. `critere_lissage = "laml"` sous `methode = "wh_quadratique"` est **refusé** (D3) par le motif **`critere_lissage_non_admis`** (module `lissage`, message qui nomme la méthode et le critère), levé par le contrôle de domaine des gouvernants, **avant** le contrôle de présence de `parametre_lissage` et d'`intervalle_lissage` (point 3.2) : un tel plan ne reçoit pas `parametre_manquant` pour `parametre_lissage`. `parametre_lissage` porte **h** sous (a) et **λ** sous (b), grandeurs d'échelles différentes (pénalité sur q sous (a), sur ln μ sous (b)) : le rapport figé et la documentation les nomment selon `methode` (« h » ou « λ ») et ne les comparent jamais d'une variante à l'autre.

3.5. **Fonctions de contrôle du module** : `controler_parametres_lissage()` reçoit chaque paramètre du catalogue de l'étape par son nom (argument formel par paramètre, absent = `missing()`), et un test lie ses arguments formels aux noms du catalogue (critère local ; la règle générale de #205 reste à `claude/rejeu-suites`).

3.6. **Options écartées.** (a) *Fusionner `recette` dans une colonne de condition unique* (`condition_sur = "recette"` ou nom d'un paramètre) : une seule notion, mais deux moments d'évaluation (avant et après les rôles) cachés derrière une colonne, réécriture de `controler_parametres_recette()` et des lieux admis de `recettes_invariant.R` (ADR 0016, annotation du 10/11/2026, (c)) sans gain ; laissée au mainteneur (point C). (b) *Conjonctions ou disjonctions de conditions* : langage de conditions, déjà écarté par l'ADR 0016, point 5.6 (c). (c) *Une étape par variante* (`lissage_quadratique`, `lissage_poisson`) : deux étapes productrices pour une même famille, `ETAPES`, la matrice et le rapport doublés ; la règle 2.2 les refuserait ensemble, ce qui est juste, mais la méthode 4 en ajouterait une troisième. ### 8. Classe de tolérance des grandeurs issues d'un calcul itératif ou d'une optimisation (F8)

8.1. **Constat.** Sur la plateforme de référence, la construction est identique au bit près ; la tolérance ne sert qu'à absorber un écart numérique bénin (réordonnancement d'opérations, `libm`). Une grandeur issue d'une boucle arrêtée sur un critère (PIRLS, arrêt sur ε_d) ou d'une optimisation (λ̂ par Brent) peut, sous une perturbation de l'ordre de l'unité d'arrondi, s'arrêter à une itération voisine ou en un point voisin : l'écart n'est plus borné par l'arithmétique mais par la tolérance de l'algorithme.

8.2. **Décision.** Une classe nouvelle de `CLASSES_TOLERANCE`, nom indicatif `optimisation`, dont la **valeur est fixée par une mesure**, non par cet ADR : au commit (3) (#225), `coder` mesure, sur les plans de référence de (b), l'écart relatif de λ̂, ν, LAML et `qx` entre l'exécution nominale et des exécutions perturbées de l'ordre de l'arrondi (départ de la grille décalé d'une unité de dernier rang, ordre de sommation modifié), et propose la plus petite classe décimale qui couvre dix fois l'écart maximal mesuré ; avis d'`actuary` ; **annotation datée de l'ADR 0009** au même commit (points 3.3, 3.4, 9.3). *Voir l'ADR 0009, annotation du 12/11/2026 : classe `optimisation` = 1e-3 (constat de mesure, au-delà du seuil de 1e-6 de M416, acceptée par `actuary-approfondi` sous M420, (4)), portée `lissage/*` (M416).*

8.3. **Portée.** Les clés étant par chemin et non par méthode, et `table_lissee/qx` étant le même chemin sous (a) et (b), la classe vaut pour les chemins de l'étape `lissage` qui reçoivent une valeur itérée sous (b) (`qx`, bornes de crédibilité, ν, LAML, λ̂), y compris sous (a) ; la perte de sensibilité sous (a) est couverte par les tests unitaires (critères A1 à A6 de #223, contre-vérification `WH` à 1e-10). Les grandeurs de la validation `lissee` qui dérivent de ces valeurs (attendus, X², ddl) reçoivent la même classe par leurs clés propres. Le nombre d'itérations (`integer`) est exact. *Voir l'annotation du 11/11/2026, point 5.5.* *Voir l'ADR 0009, annotation du 12/11/2026 : classe `optimisation` = 1e-3, portée `lissage/*` (M416 prévaut sur la phrase « Les grandeurs de la validation `lissee` […] par leurs clés propres » du présent point : ces chemins gardent 1e-12).*

8.4. **Options écartées.** (a) *Classe 1e-10 existante, sans mesure* : chiffre non justifié. (b) *Clés qualifiées par la méthode* : la clé dépendrait du plan, contre l'ADR 0009 (une clé par chemin, `CONTEXT.md`, « Classe de tolérance »). (c) *Noms de chemins distincts par méthode* (`table_lissee_quadratique`, `table_lissee_poisson`) : casse le contrat 1.2 pour un besoin de test.

8.5. **Effet sur les résultats** : aucun pour R1 à R14.

### 9. Méthode numérique (F9)

9.1. **R de base, sans dépendance ni code compilé** (ADR 0002, point 6). Systèmes de (a) et de chaque itération de (b) résolus par **QR des moindres carrés augmentés** [W^{1/2} ; √h K] par `qr()` avec `LAPACK = FALSE` (routine `dqrdc2` de R), puis `qr.coef()` ; rang exigé égal à n (sinon erreur de programmation : le refus « moins de z cellules de poids non nul » le précède) ; aucune inversion explicite ni équation normale (mesure d'`actuary` : conservation perdue à 5,2e-4 par résolution dense à λ = 10¹², ≤ 3,6e-10 par QR). K = `diff(diag(n), differences = z)`. ln|W + P_λ| se lit sur la diagonale du facteur R (|det| invariant par la permutation) ; ln|P_λ|₊ par `eigen(symmetric = TRUE)` de KᵀK, qui ne dépend que de n et z.

9.2. **Coût** : 1,14 ms par décomposition 240 × 121 (*vérifié*, point « Contexte ») ; un choix de λ par LAML (grille, puis Brent, PIRLS complet par point) demande de l'ordre de 10³ décompositions par segment, soit de l'ordre de la seconde : sans Cholesky en bandes (`Matrix` exclu, ADR 0002) ni code compilé. Mesure de la durée réelle au commit (3) par un script de `tests/mesures/` (hors CI), citée dans le commit ; optimisation seulement sur mesure de lenteur documentée.

9.3. **Constantes** (D12) : ε, ε_d, plafond d'itérations, grille de ln λ, tolérance de Brent, constantes du module `lissage`, recopiées dans `parametres` (point 6.1), chacune documentée « tirée de la source » ou « non tirée de la source ».

9.4. **Reproductibilité** : ni aléa ni graine ; résultat au bit près sur la même machine ; d'une machine à l'autre, classe du point 8. `qr(LAPACK = FALSE)` emploie des BLAS de niveau 1 et `eigen()` LAPACK : couverts par la plateforme de référence (ADR 0008).

- ordre entre segments (D3) en **trois vecteurs parallèles** de même longueur k ≥ 0 (noms indicatifs `ordre_variable`, `ordre_superieur`, `ordre_inferieur` ; longueur 0 explicite admise), sur le précédent de la provenance de k fichiers (ADR 0016, point 8.5 (d) : vecteurs parallèles plutôt que liste de triplets, grammaire du plan inchangée).

13.3. **Tables de référence en comparaison** : `etapes/coherence_regularite/tables_reference` s'ajoute à `PARAMETRES_CLE_TABLE` ; `cles_citees()` lit un vecteur de clés (une clé par élément). C'est un **écart à la lettre** de l'ADR 0015, point 1.2 (« une chaîne unique, la clé ») : un paramètre peut citer k ≥ 0 clés ; les contrôles 1.3 et 7 bis s'appliquent à chaque clé, inchangés. Contrôle d'entrée de chaque table citée : plage couverte, table sans `annee` (refus en v1, spécification de #144) ; la convention d'âge n'est pas exigée pour une table de référence évaluée seule.

*Complément du 11/11/2026 (relecture d'`actuary`), précision de rédaction pour `docwriter`.* La comparaison à des tables de référence (D1 (a) de #144) est un choix de l'outil ; elle **n'est pas à attribuer à la p. 36** des Lignes directrices (2006). La documentation (étape (6) de B19) et le rapport figé ne citent pas cette page comme source de la comparaison.

13.4. **Lecture des tables** : la table construite par le seam du point 1.5 ; chaque table de référence en `table_reference` (ADR 0007, point 7.1), ses « segments » étant ses modalités de sexe. L'application du critère C3 (ordre entre segments) à une table de référence est une **question pour `actuary`** (Q1 ci-dessous) ; la forme admet les deux réponses.

*Décision (M415, Q1 d'`actuary`).* Le critère C3 s'applique **aussi** aux tables de référence évaluées en comparaison, sous trois conditions :
1. seuls les triplets d'ordre dont la variable est `sexe` s'appliquent à une table de référence ;
2. et seulement si la table porte les deux modalités de sexe du moteur : `MODALITES_SEXE` (`H`, `F` ; `R/donnees.R:91` à `fedd350`) inclus dans les sexes de la table, valeurs de `SEXES_TABLE` (`R/donnees.R:2039`) ;
3. une table de référence `ensemble` seule, ou un triplet sur une autre variable que `sexe`, donne l'état **`sans_objet`** pour ce couple (table, triplet), **pas un refus**.

Texte de statut de C3 sur une table de référence : « choix de l'outil, à finalité comparative, non prescrit par II.3 ». La convention d'âge de chaque table évaluée est restituée. Constat de forme (*vérifié* par lecture de `table_reference()`, `R/donnees.R:2053` à `fedd350`) : l'objet `table_reference` ne porte aucun champ de convention d'âge ; la façon de restituer la convention d'une table de référence (mention lue dans la source ou « non portée par la table ») est à fixer par la spécification de forme (0')(b) d'`actuary-approfondi`, avant le code de #144.

13.5. **Restitution** (noms indicatifs) : `parametres` (paramètres, `reference_methode`, statuts) ; `resultat$ages` (table, segment, âge → g, δ1, δ2, inégalités), `resultat$ordre_segments`, `resultat$regularite` (table, segment, z → m_z, S_z, r̂, S^L, état) ; `diagnostics` (décomptes, en `integer`). S_z par la fonction du point 10.3.

*Complément du 11/11/2026 (relecture d'`actuary`).* S_z de #144 est **toujours** calculé sur la colonne `qx` de la table évaluée (table construite ou table de référence), à l'échelle q (D6 de #144 : S_z sur ln μ non retenu) ; il n'est **jamais** repris du S de l'étape `lissage`, qui porte sur ln μ sous (b) (`echelle_penalite`, point 10.3). C'est l'appelant (`calculer_coherence_regularite()`, indicatif) qui passe `qx` à la fonction partagée du point 10.3 ; celle-ci ne connaît ni l'échelle ni la table.

13.6. **Options écartées.** (a) *Intégrer les critères à l'étape `validation`* : ni observation ni H0 (motif du retrait de #4, Q8) ; les objets de R8 à R13 changeraient.
