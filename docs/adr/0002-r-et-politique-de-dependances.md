# R 4.3.1, moteur en R de base, packages avancés cantonnés à la contre-vérification hors CI, R pur mesuré avant tout code compilé

*(16/10/2026, décision M43 : version du projet portée à R 4.3.3 ; le titre garde la version décidée le 14/10/2026 ; quatrième annotation du 16 octobre 2026, A13.)*

## Contexte

Le projet construit des tables d'expérience destinées à des dossiers ACPR (`docs/cadrage/2026-10-14-entretien-cadrage.md`, Q1) : la traçabilité et la relecture priment sur la vitesse de développement. Le langage et la politique de dépendances conditionnent la forme du moteur (ADR 0004), les batteries de tests, la reproductibilité (`CLAUDE.md`, « Changements de résultats ») et la durée de vie du code.

Faits qui pèsent (`docs/recherche/2026-10-14-cadre-tables-experience.md`, § 3, pages CRAN et PyPI lues le 14/10/2026) :

- l'écosystème R couvre tout le périmètre visé (Q30), mais ses packages de référence sont fragiles : `MortalitySmooth` est **archivé du CRAN depuis le 10/12/2020** (dépendance `svcm` archivée) [vérifié], sans successeur trouvé [non trouvé] ; `StMoMo` 0.4.1 date du **13/04/2018**, dernier commit GitHub le 02/11/2019, 17 issues ouvertes [vérifié] ; `ELT` 1.7 (2023) dépend de `xlsx` (Java) [vérifié] ; `WH` 2.0.0 (2025) s'appuie sur `Rcpp` et LAPACK [vérifié] ;
- en Python, `lifelines`, `scikit-survival` et `statsmodels` couvrent l'estimation brute et les GLM [vérifié] ; la recherche n'a trouvé **aucun équivalent mûr** de `StMoMo` ni de `MortalitySmooth` après trois recherches ciblées [non trouvé : les candidats sont pédagogiques ou en version 0.x] ; prospective et lissage 2D seraient à réécrire (§ 3.b) ;
- un package tiers dans le moteur fait dépendre un résultat soumis à l'ACPR d'un code que l'équipe ne relit pas, dont la version peut changer ou disparaître ; la revue indépendante (`outil_USP`, `docs/exigences.md` § 4.1) suppose que tout calcul soit lisible dans le dépôt ;
- **contrainte non visible dans le code** (mainteneur, 14/10/2026, interprétation I1) : le **poste de travail** du mainteneur pourrait ne pas permettre l'installation de packages CRAN — ni les packages avancés, ni les accélérateurs en C / C++ (`Rcpp`), ni peut-être Rtools. C'est la raison première de la règle « R de base » ; ce qui est réellement installable là-bas n'est pas encore mesuré (issue #2 : relevé par le mainteneur, groupe par groupe).

Mesure du 14/10/2026 sur le poste du mainteneur (`Rscript -e 'installed.packages()'`, R 4.3.1 ucrt, seule version présente dans `C:/Program Files/R`) : packages de priorité `base` = `base compiler datasets graphics grDevices grid methods parallel splines stats stats4 tcltk tools utils` ; `survival` et `mgcv` sont de priorité `recommended` (avec `boot class cluster codetools foreign KernSmooth lattice MASS Matrix nlme nnet rpart spatial`). Q14 range `survival` et `mgcv` parmi les packages de contre-vérification : « packages livrés avec R » s'entend donc **priorité `base`**, et non `recommended`. *(16/10/2026, décision M43 : le mainteneur précise que son poste de travail a **R 4.3.3**, et non 4.3.1 ; la mesure ci-dessus n'est pas réécrite, l'écart est consigné dans la quatrième annotation du 16 octobre 2026, A13.)*

## Décision

Arrêtée par le mainteneur le 14/10/2026 (Q4, Q14, Q24, Q38, Q39) :

1. **Langage : R** (Q4 : Python jugé meilleur en vitesse et en interface, mais plus long à développer). Interface : application Shiny locale (Q5 ; ADR 0004).
2. **Version : R 4.3.1**, celle d'`outil_USP` (Q39), **contre la recommandation de la session** (« dernière version stable »). La CI et la plateforme de référence des non-régressions fixent 4.3.1 ; `DESCRIPTION` déclare `R (>= 4.3.1)`. Un changement de version est une décision du mainteneur, consignée par annotation datée du présent ADR, avec les écarts de résultats mesurés. *(16/10/2026, décision M43 : version portée à **R 4.3.3** pour la CI, la plateforme de référence des non-régressions et le poste ; `DESCRIPTION` proposé à `R (>= 4.3.3)` ; aucun écart de résultat, aucun code ; quatrième annotation du 16 octobre 2026, A13 et A14. Même jour, décision M44 : `DESCRIPTION` déclare `Depends: R (>= 4.3.3)`, lecture proposée de A14 retenue.)*
3. **Moteur en R de base** (Q14, option a) : le package `tablexp` n'importe que les packages de priorité `base` listés ci-dessus (`Imports` et `Depends` de `DESCRIPTION` ; vérification par script en CI). Les packages `recommended` (dont `survival`, `mgcv`, `Matrix`, `MASS`) en sont exclus au même titre que les packages CRAN.
4. **Packages avancés en contre-vérification, hors moteur et hors CI** (Q14 ; Q24, option A) : `survival`, `mgcv`, `WH`, `ELT`, `StMoMo`, `demography`, `MortalityLaws`, `lifecontingencies`, `survPen` (liste étendue sur avis d'`actuary`) produisent des **valeurs de référence externes**, écrites en dur dans les tests avec la version de chaque package et la date, par un script hors CI exécuté à la main. La CI n'installe aucun d'eux. Régénération sur ordre du mainteneur seulement, avec tableau avant / après. *(16/10/2026 : `ELT` retiré de la liste, il dépend de Java ; voir l'annotation du 16 octobre 2026, A1 et A5. Même jour, décision M42 : liste étendue à `MortCast`, `locfit` et, à titre facultatif, `flexsurv` ; exécution possible sur un autre poste muni d'un R récent ; source d'`ELT` exécutable hors du dépôt en appoint ; troisième annotation du 16 octobre 2026, A9 à A12.)*
5. **Passage à un package tiers enveloppé dans le moteur** (Q14, option b : un package par méthode, derrière un adapter) : uniquement par un nouvel ADR, méthode par méthode, après démonstration qu'une réimplémentation en R de base est impossible ou déraisonnable. **Voie de réouverture prévue** (I1) : une fois le relevé de l'issue #2 rendu, un package **disponible sur le poste de travail** qui apporte une accélération (C / C++) ou une méthode peut être admis dans le moteur — ou, pour les packages de contre-vérification, dans les tests exécutables sur ce poste — par annotation datée du présent ADR qui cite le relevé, puis ADR par méthode s'il entre dans le moteur. Tant que le relevé n'est pas rendu, le point 3 s'applique sans exception. *(16/10/2026 : relevé rendu, condition levée ; critères d'évaluation d'un package candidat : annotation du 16 octobre 2026, A2 et A3.)*
6. **R pur d'abord, mesuré** (Q38) : chaque méthode est écrite en R de base et chronométrée sur le simulateur (Q33) à la volumétrie cible (Q7 : millions de lignes, dizaines d'années). Du code C n'est admis que sur **mesure de lenteur documentée** (commande, temps, machine), par l'**interface native de R** (`.Call`, en-têtes `R.h` et `Rinternals.h`), **sans `Rcpp`**, et par ADR. *(16/10/2026, décision M41 : « sans `Rcpp` » est levé ; le code compilé admis peut être écrit par l'interface native ou en C++ par `Rcpp`, le reste du point est maintenu ; voir la seconde annotation du 16 octobre 2026, A8.)*
7. **Lecture et écriture des fichiers hors moteur** (Q37, Q11) : `openxlsx` est admis dans l'application, jamais dans `tablexp` ; le CSV passe par R de base.

## Options écartées

- **Python** (`lifelines`, `statsmodels`, interface Streamlit, Dash ou NiceGUI, § 3.b et § 3.c) : couverture incomplète du périmètre (prospective et lissage 2D à réécrire), préférence et pratique du mainteneur (Q4), continuité avec `outil_USP` dont les dispositifs sont repris (Q8). La vitesse de Python n'est pas déterminante tant que le R pur n'a pas été mesuré trop lent (point 6).
- **Dernière version stable de R** (recommandation de la session) : écartée par le mainteneur (Q39). Risque assumé : un package de contre-vérification récent peut exiger un R plus récent ; le script hors CI consigne alors la version installable sous 4.3.1, ou la contre-vérification se fait sur un autre poste avec sa version de R consignée. *(16/10/2026, décision M42 : la seconde voie est retenue ; troisième annotation du 16 octobre 2026, A11. Même jour, décision M43 : la version du projet passe à 4.3.3, toujours de la série 4.3 ; le risque assumé est inchangé, quatrième annotation, A15.)*
- **Packages tiers dans le moteur, option (b)** : garde une dépendance par méthode vers un code non relu, dont `MortalitySmooth` montre qu'il peut disparaître ; réservée à un ADR ultérieur (point 5). **Option (c)**, usage libre du CRAN dans le moteur : rend la revue indépendante impossible et les résultats tributaires des versions installées.
- **Contre-vérification en CI** (Q24, option B) : la CI installerait les packages avancés à chaque exécution ; une archive CRAN, une mise à jour ou une panne réseau ferait échouer la batterie sans qu'aucun résultat du moteur ait changé, et la valeur de référence ne serait plus figée. Incompatible avec « un chiffre ne se recopie pas, il se remesure » appliqué à une référence : elle doit être écrite, datée et versionnée.
- **`Rcpp`** : package tiers dans le moteur (contredit le point 3), chaîne C++ qu'un relecteur R ne lit pas ; l'interface native suffit pour une boucle numérique. *(16/10/2026 : option rouverte et retenue par le mainteneur, décision M41 ; ses deux objections sont reportées sur l'ADR de méthode qui introduit `Rcpp` : seconde annotation du 16 octobre 2026, A8.)*

## Conséquences

- Fichiers : `DESCRIPTION` de `tablexp` (`Depends: R (>= 4.3.1)`, `Imports` limités aux packages `base`) ; script de CI qui échoue si `Imports` ou `Depends` sort de la liste ; scripts de contre-vérification hors CI, versions et dates consignées dans chaque fichier de valeurs ; `README.md` (installation sous 4.3.1) ; `CLAUDE.md`, « Architecture » et « Changements de résultats » (plateforme de régénération : R 4.3.1) ; `docs/exigences.md` : E4.1, E4.2, E4.7, E4.8. *(16/10/2026, décision M43 : lire 4.3.3 partout où ce point écrit 4.3.1 ; quatrième annotation, A14. Même jour, décision M44 : `Depends: R (>= 4.3.3)` confirmé ; le script de CI contrôle aussi `LinkingTo`, A8.)*
- Effet sur les résultats : aucun à ce jour (aucun code). À terme, chaque méthode est une réimplémentation : les écarts aux packages de référence sont attendus, bornés par une tolérance déclarée dans le test, jamais masqués.
- Coût accepté : réécrire en R de base les lissages pénalisés (Whittaker-Henderson, P-splines : matrices denses sans `Matrix`, bases B-splines par `splines`), les estimateurs de survie et, en v2, les modèles prospectifs ; `parallel` (base) reste disponible pour le bootstrap (Q31).
- Ce que l'ADR ne règle pas : la liste des packages de contre-vérification par méthode (avis d'`actuary`, Q30) *(avis rendu le 16/10/2026, `partiel` ; troisième annotation, A9 et A10)* ; le seuil de lenteur qui justifie du C (fixé à la première mesure, Q38) ; la politique de montée de version de R (annotation ici) ; **ce qui est installable sur le poste de travail** — packages, Rtools, accès au CRAN — et donc où les contre-vérifications peuvent s'exécuter et si le C du point 6 y est compilable (issue #2 ; tant que Rtools n'y est pas établi, le point 6 reste théorique sur ce poste). *16/10/2026 : point réglé pour le poste de travail (tout est installable sauf `ELT`, Java exclu ; Rtools présent ; CRAN accessible) ; ce qui reste ouvert est listé dans l'annotation du 16 octobre 2026.*
- Vocabulaire : `CONTEXT.md`, « Mesure », « Tableau avant / après », « Visa », « Contre-vérification ».

Issues : #2 (relevé des packages installables sur le poste de travail ; rendu le 16/10/2026, voir l'annotation ci-dessous).

## Annotation du 16 octobre 2026 — relevé du poste de travail (issue #2), absence de Java, critères d'admission d'un package tiers

Décision du mainteneur du 16/10/2026 (feuille de route, M40), rendue dans la conversation avec la session principale. Elle clôt le relevé de l'issue #2 ; la décision du 14/10/2026 ci-dessus n'est pas réécrite, elle est complétée comme suit.

**Relevé.** Rapporté par le mainteneur, sans sortie du script de l'issue #2 collée (relevé déclaratif ; versions, miroir et type d'installation non consignés) :

- tous les packages des groupes A (interface et fichiers), B (`recommended`), C (contre-vérification) et D (accélération ou commodité) de l'issue #2 s'installent sur le poste de travail, **sauf `ELT`**, qui dépend de `xlsx`, donc de Java, inutilisable sur ce poste ;
- **Rtools est installé** ; l'accès au CRAN fonctionne pour installer des packages.

Les versions effectivement installées seront consignées par le script de contre-vérification hors CI (point 4), à chaque génération de valeurs, et par l'ADR de méthode pour tout package admis dans le moteur (A3).

**A1. Contrainte de plateforme : absence de Java.** Le mainteneur la pose comme la seule contrainte du poste de travail pour ce projet. Aucun code du projet ne dépend de Java, ni directement ni indirectement (`Depends`, `Imports`, `LinkingTo`, récursivement ; par exemple `rJava`, `xlsx`) : ni le moteur, ni l'application, ni la contre-vérification. La disponibilité d'un package qui ne figure pas dans le relevé est vérifiée par le mainteneur sur son poste, à la demande, avant toute décision qui l'emploie.

**A2. Fin de la condition du point 5.** Le relevé étant rendu, la phrase « Tant que le relevé n'est pas rendu, le point 3 s'applique sans exception » est caduque. Le **point 3 reste la règle par défaut** : le moteur est écrit en R de base. L'exception du point 5 est ouverte **sans autre préalable** : un package disponible sur le poste de travail et sans Java (A1) peut entrer dans le moteur par un **ADR propre à chaque méthode**, derrière un adapter (point 5, Q14 option b).

**A3. Critères d'évaluation d'un package candidat au moteur**, instruits dans l'ADR de la méthode. Le mainteneur demande d'évaluer deux gains :

- **temps de développement** : ce que la réimplémentation en R de base coûterait (fonctions à écrire, à tester et à documenter), comparé à l'adapter autour du package ;
- **efficacité** : gain apporté par du code compilé (C, C++, Fortran) que le package intègre, **mesuré** comme au point 6 (chronométrage du package et du R pur sur le simulateur à la volumétrie cible, commande, temps, machine) ;

à mettre en balance avec les critères déjà posés par le présent ADR : **traçabilité et lisibilité** (le calcul doit rester explicable à un relecteur externe : méthode publiée et citée, source accessible) ; **pérennité** (date de la dernière version, maintenance, dépendances ; `MortalitySmooth` archivé en 2020 et `StMoMo` sans version depuis 2018 en sont les contre-exemples) ; **reproductibilité** (version fixée, consignée dans la fiche de construction, E3.6) ; **absence de Java** (A1). Deux points restent à instruire par chaque ADR de méthode : la manière dont la CI installe et fige la version du package admis (la phrase « La CI n'installe aucun d'eux » du point 4 vise la contre-vérification, pas un package admis dans le moteur) et la liste blanche du script de CI qui contrôle `Imports` et `Depends` (point 3).

**A4. Contre-vérification exécutable sur le poste du mainteneur.** Le point 4 devient praticable sur le poste de travail : le script de contre-vérification s'y exécute, à la main, **toujours hors CI** ; le reste du point 4 est inchangé (valeurs en dur, version et date de chaque package, régénération sur ordre du mainteneur avec tableau avant / après). *(Même jour, décision M42 : le poste de contre-vérification n'est pas forcément le poste de travail ; troisième annotation, A11.)*

**A5. `ELT` sort de la liste de contre-vérification** (A1). Liste du point 4 désormais : `survival`, `mgcv`, `WH`, `StMoMo`, `demography`, `MortalityLaws`, `lifecontingencies`, `survPen`. Aucun document du dépôt ne désigne de remplaçant. Selon la recherche du 14/10/2026 (`docs/recherche/2026-10-14-cadre-tables-experience.md`, § 3.a, ligne `ELT` ; § 1.b, II1291-15 ; § 2.e), `ELT` porte les méthodes 1 à 4 de positionnement de l'Institut des actuaires, les validations `ValidationLevel1-3` et la fermeture de Denuit et Goderniaux (2005) (`CompletionA/B`), et le guide II1291-15 s'appuie sur lui : ces méthodes n'ont plus de contre-vérification par package désignée. Le choix d'une contre-vérification de remplacement (autre package, seconde source, seconde transcription au sens de `CONTEXT.md`, « Contre-vérification ») revient à `actuary`. Les autres packages du groupe C relevés installables (`MortalityTables`, `MortCast`, `flexsurv`, `relsurv`, `HMDHFDplus`, `BayesMortalityPlus`, `StanMoMo`) n'entrent dans la liste que sur avis d'`actuary` (point 4, « liste étendue sur avis d'`actuary` »). *(Même jour : avis d'`actuary` rendu et décision M42 ; contre-vérification par méthode et liste étendue : troisième annotation, A9 et A10.)*

**A6. Rtools rend le point 6 praticable sur le poste de travail** : du code C par l'interface native y est compilable. Le point 6 est inchangé (R pur d'abord, C sur mesure de lenteur documentée, par ADR) ; le seuil de lenteur reste à fixer à la première mesure (Q38). *(Même jour : la modalité « sans `Rcpp` » du point 6 est levée par A8.)*

**A7. Tension entre le point 6 et le critère d'efficacité (interprétation à confirmer par le mainteneur).** Le point 6 admet du C « sans `Rcpp` », et les options écartées rejettent `Rcpp` ; le critère A3 retient au contraire, comme gain recevable, le code compilé qu'un package intègre, souvent du C++ par `Rcpp` (`WH` en est un exemple, Contexte ci-dessus). Lecture proposée, **non confirmée** : le point 6 et l'option écartée « `Rcpp` » visent le **code compilé écrit par le projet** dans `tablexp` (interface native seulement, jamais `Rcpp` dans nos sources) ; un **package tiers** qui embarque du C ou du C++, y compris par `Rcpp`, relève du point 5 et de A3, `Rcpp` n'étant alors qu'une dépendance indirecte de ce package. Lecture alternative : « sans `Rcpp` » exclut aussi du moteur tout package tiers construit sur `Rcpp`, ce qui écarterait `WH` et réduirait le critère d'efficacité aux packages en C ou en Fortran. Tant que le mainteneur n'a pas tranché, un ADR de méthode qui propose un package construit sur `Rcpp` cite la présente annotation et demande sa décision. *(Tranchée le 16/10/2026 par le mainteneur, décision M41 : ni l'une ni l'autre lecture, `Rcpp` est admis partout ; voir A8.)*

**Effet sur les résultats** : aucun (aucun code).

**Ce que la présente annotation ne règle pas** : le remplaçant d'`ELT` en contre-vérification (`actuary`) ; l'extension de la liste du point 4 aux autres packages du groupe C (`actuary`) *(ces deux points : avis d'`actuary` du 16/10/2026 et décision M42, troisième annotation, A9 et A10)* ; la lecture de A7 (mainteneur ; *tranchée le même jour, A8*) ; le contrôle mécanique de l'absence de Java (dépendances récursives de `tablexp`, de l'application et du script de contre-vérification), qui appelle un script (`CLAUDE.md`, « Workflows », principe 7) ; la compatibilité de licence entre un package admis dans le moteur et la licence du dépôt (PolyForm Noncommercial 1.0.0, M12), à examiner dans chaque ADR de méthode.

## Seconde annotation du 16 octobre 2026 — `Rcpp` admis pour le code compilé du projet comme pour les packages tiers (décision M41)

Décision du mainteneur du 16/10/2026 (feuille de route, M41), en réponse à la question de la session principale qui portait la lecture de A7. Elle révise le point 6 et rouvre l'option écartée « `Rcpp` » ; le texte du 14/10/2026 et la première annotation du 16/10/2026 ne sont pas réécrits (mentions datées aux endroits concernés).

Question posée : « L'ADR 0002 interdit `Rcpp` pour notre propre code C (point 6). Un package tiers qui embarque du C++ par `Rcpp` (par exemple `WH`) peut-il entrer dans le moteur par un ADR de méthode ? » Options proposées : (1) oui, par ADR, l'interdiction ne visant que le code du projet (lecture proposée de A7) ; (2) non, lecture stricte (lecture alternative de A7) ; (3) `Rcpp` admis partout, y compris pour le code compilé écrit par le projet, ce qui rouvre le point 6 et demande un ADR qui le révise. **Le mainteneur a choisi (3).**

**A8. `Rcpp` admis ; ce qui reste du point 6.**

- **A7 est tranché** : `Rcpp` n'est plus exclu, ni comme dépendance indirecte d'un package tiers, ni dans les sources de `tablexp`. Un package tiers construit sur `Rcpp` (par exemple `WH`) relève du point 5 et des critères A3, sans obstacle propre à `Rcpp`.
- **Point 6 révisé** : la règle « R pur d'abord, mesuré » est **maintenue** (chaque méthode est écrite en R de base et chronométrée sur le simulateur à la volumétrie cible) ; du code compilé écrit par le projet n'est admis que sur **mesure de lenteur documentée** (commande, temps, machine) et **par ADR**, comme le 14/10/2026. Seule la modalité change : ce code peut être écrit **par l'interface native de R** (`.Call`, en-têtes `R.h` et `Rinternals.h`) **ou en C++ par `Rcpp`**. L'ADR de méthode motive le choix entre les deux (lisibilité pour un relecteur R, coût d'une dépendance supplémentaire). Le seuil de lenteur reste à fixer à la première mesure (Q38).
- **Option écartée « `Rcpp` » du 14/10/2026 rouverte** par la présente décision. Ses deux objections ne disparaissent pas, elles changent de lieu : « package tiers dans le moteur (contredit le point 3) » est traitée par l'inscription de `Rcpp` sur la liste blanche (ci-dessous) ; « chaîne C++ qu'un relecteur R ne lit pas » est instruite dans l'ADR de méthode, au titre de la traçabilité et de la lisibilité (A3), avec la mesure qui justifie le code compilé.
- **Conséquence pour le point 3 et le script de CI** : dès que des sources de `tablexp` emploient `Rcpp`, celui-ci devient une dépendance directe du package (`LinkingTo: Rcpp` pour les en-têtes, `Imports: Rcpp` pour l'exécution, par l'usage ordinaire des packages construits sur `Rcpp`) ; c'est une exception au point 3 au même titre qu'un package tiers. **L'ADR de méthode qui introduit `Rcpp` le premier l'inscrit sur la liste blanche** du script de CI ; les ADR suivants s'y réfèrent. Le contrôle de ce script doit couvrir `LinkingTo` en plus de `Imports` et `Depends` (A3 ne citait que ces deux champs), faute de quoi une dépendance de compilation échapperait à la liste blanche.
- **Disponibilité sur le poste de travail** : `Rcpp` figure au groupe D de l'issue #2, déclaré installable, et Rtools est présent (relevé déclaratif, première annotation du 16/10/2026) ; versions non consignées.

**Effet sur les résultats** : aucun (aucun code).

**Points ouverts**, à instruire par l'ADR de méthode qui introduit `Rcpp` (ou du code compilé par l'interface native) :

- **chaîne de compilation en CI sous R 4.3.1** *(R 4.3.3 depuis la décision M43, quatrième annotation du 16 octobre 2026)* : compilateur C / C++ et en-têtes de R sur l'exécuteur de la CI (`ubuntu-24.04`, `.github/workflows/ci.yml`), et Rtools de la série 4.3 si une plateforme Windows est ajoutée ; la CI compile `tablexp` à chaque exécution dès qu'il contient du code compilé ;
- **version de `Rcpp` figée** : manière dont la CI installe une version fixée (même question que pour tout package admis dans le moteur, A3), et version consignée dans la fiche de construction (E3.6) ;
- **reproductibilité numérique du code compilé** : compilateur, options de compilation et bibliothèques d'algèbre linéaire peuvent faire varier les derniers chiffres ; la tolérance des tests de non-régression et la plateforme de régénération (R 4.3.1, `CLAUDE.md` ; R 4.3.3 depuis la décision M43) en tiennent compte ;
- **licence** de `Rcpp` au regard de la licence du dépôt (PolyForm Noncommercial 1.0.0, M12), comme pour tout package admis dans le moteur (première annotation du 16/10/2026) [non vérifié : page CRAN de `Rcpp` non consultée dans cette session].
