### Vocabulaire de conception

Le mode d'entrée est un **seam** du point d'entrée unique. Test de suppression : si la table entre par un argument propre, retirer la validation ne laisse qu'un argument facultatif inemployé et une ligne de catalogue ; si elle entre par le plan en valeurs, la retirer laisse une grammaire de plan étendue aux `data.frame` à attributs, une canonisation et une fiche chargées d'un objet qui n'est pas une déclaration. L'**adapter** vers le package pour une table embarquée est l'accesseur du point 6 ; le **module profond** reste l'écrivain unique, dont la table est le sixième consommateur (ADR 0011, annotation du 05/11/2026, (b) 4).

## Décision

Proposée par `architect-approfondi` le 06/11/2026 ; **à arrêter par le mainteneur** (questions 1 à 9 en fin d'ADR). Chaque point donne son effet sur les résultats.

### 1. Mode d'entrée : argument nommé facultatif `tables_reference`, clé citée par le plan

1.1. **Signature** : `construire_table(donnees, roles, plan, provenance = NULL, tables_reference = NULL)`. `tables_reference` est `NULL` (aucune table lue) ou une **liste nommée** (noms uniques, non vides, non `NA`, sans autre attribut que `names` ; forme exacte, #23) dont chaque élément est un objet de classe `table_reference` rendu par `table_reference()` (ADR 0007, point 7.1). Les noms de la liste sont les **clés** par lesquelles le plan désigne une table ; ils sont libres (une clé est une étiquette locale de la déclaration, le `nom` de la table est son attribut). Cinquième argument, facultatif et nommé : par la règle de l'ADR 0007, point 3.1, la signature `construire_table(donnees, roles, plan)` des ADR 0004 et 0005 et les 186 appels existants dans `tests/` (*vérifié*, `grep -c`) sont inchangés. Le point 9 de l'ADR 0014 est respecté : l'argument ne porte jamais une seconde table d'observations ; `donnees` reste le seul porteur des observations.

1.2. **Le plan cite une clé, jamais une valeur.** Un paramètre d'étape qui lit une table de référence est une chaîne unique, la clé (pour B13 : `etapes$validation$table_reference`, nom indicatif, catalogue de `PARAMETRES_ETAPES`, type `character`, domaine « clé de `tables_reference` »). Le plan reste une déclaration canonisable et sérialisable sans extension de grammaire ; `fiche$plan` porte la clé, et `fiche$tables_reference` (point 3) dit ce que la clé désignait.

1.3. **Contrôles à l'entrée de `construire_table()`**, après `valider_plan()` et avant toute étape (règle « validation entière avant toute exécution », `R/construire_table.R:216-226`), refus de module `construire_table` (noms indicatifs, fixés par `coder`) :
- `tables_reference_mal_formees` : ni `NULL`, ni liste nommée de la forme 1.1, ou un élément qui n'est pas de classe `table_reference` ;
- `table_reference_absente` : une clé citée par le plan n'est pas un nom de `tables_reference` ;
- `table_reference_inattendue` : un nom de `tables_reference` n'est cité par aucun paramètre du plan (rien n'entre sans être employé, sur le modèle de `graine_inattendue`, `:151-154`) ;
- `table_embarquee_absente`, `table_embarquee_discordante` : une table de statut `embarquee` doit être, par son empreinte de table, la table embarquée du package de même `nom` (point 6) ; le statut `embarquee` est une affirmation que le moteur vérifie, non une étiquette libre. En B13, aucune table n'étant embarquée, toute table de statut `embarquee` est refusée `table_embarquee_absente`.

L'ensemble des paramètres du plan qui citent une clé est une **constante du catalogue** de `R/construire_table.R` (colonne ou constante à côté de `PARAMETRES_ETAPES`), pour que ces contrôles soient génériques et ne dépendent pas de l'étape `validation`.

1.4. **Rejeu : `rejouer_fiche(donnees, fiche, tables_reference = NULL)`.** Troisième argument, facultatif et nommé, de même forme que 1.1, qui porte les tables de statut `importee` ou `synthetique` lues par la construction ; les tables de statut `embarquee` sont **relues par leur `nom`** dans le package (M210, (f)) et ne sont pas reçues. Attendu au rejeu : exactement les clés de `fiche$tables_reference` dont le statut n'est pas `embarquee` ; une clé manquante → `table_reference_absente`, une clé en trop → `table_reference_inattendue` (y compris une table embarquée passée par l'appelant). `rejouer_fiche()` assemble la liste complète (reçues plus relues) et appelle `construire_table()` **une seule fois** avec `fiche$roles`, `fiche$plan`, `fiche$provenance` et cette liste : elle n'exécute toujours aucune étape (ADR 0012, point 3.2 ; invariant de `CLAUDE.md`). Ce point **annote l'ADR 0012, points 3.1 et 3.10**, et précise son option écartée l. 159 : recevoir une table importée n'est pas recevoir un autre plan ou d'autres rôles, c'est recevoir une **entrée**, au même titre que `donnees` ; la fiche l'identifie par son empreinte et le rejeu la contrôle avant de construire (point 4).

1.5. **Effet sur les résultats** : aucun par le mode d'entrée (R1 à R6 ne citent aucune clé ; `tables_reference = NULL`).

### 2. Définition `tablexp table 1` : tri canonique, racine du texte, trois statuts

2.1. **Tri canonique dans `table_reference()`** (décision A). Le constructeur rend l'objet trié par rang de `sexe` dans `SEXES_TABLE` (par `match()`, jamais par un tri de chaînes ; `H`, `F`, `ensemble`), puis `annee` si présente, puis `age` ; `order(…, method = "radix")`, indépendant de la locale ; `row.names` automatiques. Le refus `table_ages_non_croissants` est **retiré** ; les refus de doublon (`table_age_double`) et de contiguïté (`table_ages_non_contigus`) sont maintenus et s'évaluent **après** le tri. Le tri fait partie de la définition `tablexp table 1` : l'empreinte d'une table ne dépend plus de l'ordre reçu (mesure du contexte : `13cc29e1…` des deux côtés). L'ADR 0011, annotation du 05/11/2026, (b) 3 (ordre reçu, proposition) est **remplacée** ; l'entrée « Empreinte » de `CONTEXT.md` est à corriger. L'ADR 0007, point 7.1, est précisé (ordre canonique rendu, refus retiré) : annotation.

2.2. **Racine du texte empreinté** (point laissé à fixer par (b) 4 ; demandé par `actuary`) : l'écrivain reçoit `list(table_reference = <data.frame nu>)`, de sorte que le texte s'écrit, après la première ligne `tablexp table 1`, `@noms<TAB>character<TAB>1<TAB>"table_reference"`, puis `table_reference/@colonnes`, `table_reference/@lignes`, `table_reference/age`, `table_reference/sexe`, `table_reference/annee` (si présente), `table_reference/qx`, dans cet ordre de colonnes (ADR 0011, annotation du 05/11/2026, (b) 2), valeurs en forme « empreinte ». Le `data.frame` nu porte les seuls attributs `names`, `class = "data.frame"` et `row.names` automatiques. Constante `REPRESENTATION_TABLE <- "tablexp table 1"` dans `R/rapport.R` à côté de `REPRESENTATION_RESULTAT` (`:84`) ; fonction `empreinte_table()` dans le module `rapport` à côté d'`empreinte_donnees()` (`:667`), seule à calculer cette empreinte, appelée par `empreintes_construction()` / `assembler_fiche()` et par `rejouer_fiche()`. Racine `table_reference` et non `table` : `table` désigne la table finale dans l'objet `construction` (ADR 0007, point 6.1 ; point 5 ci-dessous).

2.3. **Table synthétique** (décision B, option (c′)). Aucune étape de `construire_table()` ne calcule une table à partir de paramètres : `table_gompertz_makeham()` et `table_constante()` restent dans `simulation` (que `R/construire_table.R` ne peut pas appeler, ADR 0007, point 2.1) et l'appelant (tests, application) passe la table rendue par `tables_reference`, statut `synthetique`, `parametres` conservés dans la fiche (point 3), empreinte sur les valeurs par la règle commune, refus commun au rejeu (point 4). Conséquence assumée, déjà décrite par l'ADR 0011, annotation du 05/11/2026, (e) : le rejeu d'une construction qui lit une table de Gompertz-Makeham sur une autre plateforme peut être refusé pour un dernier bit de la `libm` ; les `parametres` en clair permettent au tiers de recalculer la table et de mesurer l'écart. Les tests de #4 donnent les q̃ en littéraux figés (avis d'`actuary`, B) et peuvent employer le statut `importee`.

2.4. **Effet sur les résultats** : `jeu_reference()` `identical` (mesure du contexte : tri identité sur les deux tables du jeu ; `loi_effective()` trie par âge) ; le témoin de `tests/unitaires/test_donnees.R:627` devient un test de l'ordre rendu ; aucune grandeur de référence.

### 3. Fiche : champ `tables_reference`, `version_fiche` 4 → 5

3.1. **Champ nouveau `fiche$tables_reference`** : `NULL` quand le plan ne cite aucune clé (comme `provenance`, sans champ de mention : le rapport figé porte la phrase lisible, point 7) ; sinon une **liste nommée par clé**, dans l'ordre des clés de `tables_reference` reçu trié par octets (`sort(method = "radix")`, forme canonique sans dépendance à la locale), chaque élément étant la liste, **dans cet ordre** : `nom`, `statut`, `source`, `forme_origine`, `parametres` (`NULL` sauf statut `synthetique`), `representation` (`tablexp table 1`), `empreinte` (MD5). Ce sont exactement les champs fixés par l'ADR 0011, annotation du 05/11/2026, (c), auxquels s'ajoute la clé comme nom d'élément. Le champ est dans le **périmètre de l'empreinte du résultat** (`CHEMINS_HORS_RESULTAT`, `R/rapport.R:749-751`, inchangé) : l'empreinte du résultat identifie aussi la table et ses métadonnées. Aller-retour texte vérifié sans extension de grammaire (contexte).

3.2. **Place** : `ORDRE_CHAMPS_FICHE` (`R/rapport.R:983-991`), bloc « données », après `empreintes` et avant `plan` : une table de référence est une entrée, à côté des rôles, de la provenance et des empreintes. `BLOCS_LECTURE_FICHE$rejeu` (`:1089`) l'ajoute aux champs lus par le rejeu ; `SECTIONS_RAPPORT` lui donne une section (ADR 0012, seconde annotation du 24/10/2026, (b) 4 : rien n'est omis en silence).

3.3. **`VERSION_FICHE` 4 → 5**, `VERSIONS_FICHE_REJEU` suivant par expression (ADR 0012, seconde annotation du 24/10/2026, (a) 9), porté par le **commit (1) de B13, #73**, premier commit qui change la définition de la fiche (ADR 0011, point 10 (a) et (c)) ; seul incrément de `version_fiche` de la branche : #4, #69 et #31 n'ajoutent aucun champ à la fiche (#69, Q4 (a), M215 ; #4 : grandeurs dans l'objet et le rapport, point 5), et le paramètre `relation` du point 8 vit dans `fiche$plan`. Une fiche de version 4 est refusée au rejeu par `version_fiche_non_admise`, sans migration (ADR 0012, point 3.5).

3.4. **Effet sur les résultats** (R1 à R6, tableau avant / après du commit (1), visa d'`actuary`, régénération unique (R)) : `fiche/version_fiche` 4 → 5 ; `fiche/@noms` (un nom de plus) ; une ligne nouvelle `fiche/tables_reference<TAB>NULL<TAB>0` ; `fiche/empreintes/resultat` (par voie de conséquence) ; le jeton de l'empreinte du code. Aucune table finale, aucun verdict, aucune autre grandeur ; toute autre ligne serait une régression.

### 4. Rejeu : contrôle 7 bis, après l'empreinte des données, avant `construire_table()`

4.1. **Forme** : le contrôle 2 de l'ADR 0012, point 3.4 (`fiche_non_conforme`) couvre aussi `tables_reference` (`NULL`, ou liste nommée d'éléments aux sept champs de 3.1, `representation` et `empreinte` chaînes uniques, `statut` dans `STATUTS_TABLE`).

4.2. **Contrôle 7 bis**, pour chaque élément de `fiche$tables_reference`, dans l'ordre des clés, arrêt au premier refus (module `construire_table`, noms indicatifs) :
1. `representation` égale à `REPRESENTATION_TABLE`, sinon `representation_table_non_admise` (raisonnement du contrôle 5 : une empreinte calculée sous une autre définition n'est jamais égale, et le refus aurait un motif trompeur ; ADR 0011, annotation du 05/11/2026, (g)) ;
2. **origine** : statut `embarquee` → table relue par `nom` (point 6), sinon `table_embarquee_absente` ; autre statut → élément de `tables_reference` de même clé, sinon `table_reference_absente` ; clé reçue en trop → `table_reference_inattendue` ; élément qui n'est pas un objet `table_reference` → `tables_reference_mal_formees` ;
3. **empreinte de table recalculée** par `empreinte_table()` sur la table obtenue, comparée à `empreinte` : sinon **`empreinte_table_discordante`** (M210, (f)) ; le message cite la clé, le `nom` et le `statut` lus, l'empreinte lue et l'empreinte calculée, rappelle que la table est une entrée de la construction et que l'effet d'une autre table se mesure par `construire_table()`, et, pour une table embarquée, qu'un package plus récent a pu corriger la table (règle durable de l'ADR 0006, « Conséquences »). Règle de rédaction de l'ADR 0007, point 6.4.

Les métadonnées (`nom`, `source`, `forme_origine`, `parametres`, et `statut` hors `embarquee`) ne sont **pas** un motif de refus : la table reçue les porte, `construire_table()` les réécrit dans la fiche rendue, et un écart apparaît au **témoin « fiche »** du bilan (ADR 0012, point 3.6) — c'est le partage voulu entre ce qui identifie l'entrée (l'empreinte, refus) et ce qui la décrit (témoin).

4.3. **Bilan** : une ligne de contrôle `tables_reference` (attendu : clés et empreintes lues ; lu : clés et empreintes recalculées, origine « reçue » ou « relue dans le package » ; verdict « conforme » ; statut « exacte ; sans rôle de sécurité »), avant les témoins ; libellés fixés par `coder`, validés par `actuary`. Un test montre que, sur `empreinte_table_discordante`, `construire_table()` n'est pas appelée (critère 3 de #86 étendu).

4.4. **Coût** : 0,037 s pour 48 642 lignes (contexte) ; l'empreinte est calculée deux fois par rejeu (contrôle, puis fiche rendue), comme celle des données (ADR 0012, point 3.7), sans changer la signature pour l'économiser.

4.5. **Effet sur les résultats** : aucun (fonction de contrôle ; R1 à R6 sans table).

### 5. Objet : aucune copie de la table ; la table de référence n'est jamais dans `table`

5.1. `x$table` désigne la **table finale** (ADR 0007, point 6.1) et reste `NULL` tant que le plan ne va pas jusqu'à l'étape `table` ; une table de référence n'y est jamais rangée (décision C). L'objet ne porte **aucune copie** de la table de référence : son identité est dans `fiche$tables_reference` ; l'étape qui la lit range dans son `resultat` les **valeurs appariées par cellule** (clé de cellule, q̃, μ̃, attendus…), qui sont des quantités du résultat au sens de l'ADR 0012, point 2.2 (le rapport les affiche sans recalcul), et dans ses `parametres` la clé et la relation déclarée. Ni `CHEMINS_HORS_RESULTAT` ni `texte_objet()` ne changent : la mesure de (h) 4 (l'écrivain refuse l'objet à attributs) n'a plus d'objet.

5.2. **Règle durable** : si une étape future doit conserver une table entière dans l'objet (par exemple une table positionnée, qui est alors un résultat), elle y range un **`data.frame` nu** (colonnes de 2.2, sans attribut de métadonnées), jamais l'objet `table_reference` ; l'identité de la table d'origine reste dans la fiche.

5.3. **Effet sur les résultats** : aucun.

### 6. Table embarquée : lecture à l'installation, accesseur exporté, mise en œuvre par la branche de transcription

6.1. **Principe** (sous réserve de la branche `claude/transcription-tables-homologuees`, M228, qui l'écrit et annote l'ADR 0006, point 2, M226 ; **B13 n'embarque aucune table**) : les tables embarquées sont des fichiers **texte** sous `inst/extdata/` (`CLAUDE.md`, « Données » ; ADR 0006), chacun avec son fichier de provenance ; le package les lit **à l'installation**, par du code de premier niveau du module `donnees`, en une constante (nom indicatif `TABLES_EMBARQUEES`, liste nommée par `nom` d'objets `table_reference` de statut `embarquee`, `source` = chemin relatif du fichier de provenance, ADR 0011, annotation du 05/11/2026, (c)), par le mécanisme déjà accepté pour `EMPREINTE_CODE` (ADR 0011, cinquième annotation du 20/10/2026, (c), et M70 : répertoire courant = racine des sources à `R CMD INSTALL`, mesuré sur un paquet jouet). **Aucun fichier n'est ouvert à l'exécution** : `construire_table()` et `rejouer_fiche()` lisent une constante, et E4.4, l'ADR 0004, point 3, et l'ADR 0011, point 8.1, restent vrais à l'exécution, par le même raisonnement que pour l'empreinte du code (cinquième annotation du 20/10/2026, (c) 2).

6.2. **Accesseurs exportés** (module `donnees`, à côté de `table_reference()` ; appelants hors package : application, tests, tiers qui rejoue) : `table_embarquee(nom)` rend l'objet `table_reference` de ce nom ou refuse `table_embarquee_absente` ; `tables_embarquees()` rend le catalogue (nom, source, empreinte, première ligne). Le script de CI qui recalcule l'empreinte de chaque table embarquée et la compare au fichier de provenance (M210, (d)) lit ce même catalogue. Si la mesure de la branche de transcription (installation depuis `R CMD build`, `inst/extdata/` présent, garde sur `DESCRIPTION` comme pour `EMPREINTE_CODE`) infirmait la lecture à l'installation, le repli est `system.file()` **dans l'accesseur seulement**, consigné par annotation ; `construire_table()` ne lit jamais de fichier.

6.3. **Format du fichier texte** : laissé à la branche de transcription (ADR 0006, « Conséquences » ; contrat partagé « format des tables de référence embarquées et de leurs fichiers de provenance », `docs/agents/routage.md`, § 4.2), sous trois contraintes : lu en R de base sans évaluation ; `forme_origine = "lx"` admise, la conversion en `qx` n'employant que des opérations de base de la norme IEC 60559 (portabilité, ADR 0011, annotation du 05/11/2026, (e)) ; refus des l_x non décroissants en citant les âges (E2.26, #146).

6.4. **Effet sur les résultats** : aucun (B13 : catalogue vide ; `table_embarquee()` refuse tout nom).

### 7. Déclaration de la relation table / observations, aléa, appariement, `annee`, suivi d'expérience

7.1. **Relation** (décision C) : paramètre **requis, sans défaut**, de l'étape `validation` dans `PARAMETRES_ETAPES` (type `character`, modalités fermées), nom et libellés indicatifs `relation_table = c("independante", "ajustee_hors_outil")` ; `independante` → p = 0 ; `ajustee_hors_outil` → p-valeurs non produites, `ddl_non_etabli`. Il vit dans `fiche$plan` (canonique) ; ce n'est pas un attribut de la table (la relation décrit cette construction, pas la table). La forme (paramètre d'étape, présent ou refusé) est fixée ici, comme l'ADR 0007, point 5.2, le prévoit ; le nom exact et les libellés sont fixés par l'avis de forme (0'') et la spécification d'`actuary`.

7.2. **Aléa et #61** : `ETAPES$aleatoire` reste une **constante par étape** (ADR 0007, point 5.1 : « la liste des étapes qui tirent est une constante du package ») ; l'étape `validation` est déclarée `aleatoire = TRUE`, son paramètre `B` (réplications de Monte-Carlo, M217, Q2) est un entier **≥ 1**, sans défaut ; `B = 0` n'est pas admis. La graine est donc requise dès que `validation` est au plan, et le refus nommé de #61 (`graine_invalide`, avant `canoniser_plan()`, domaine de la canonisation) devient effectif au commit (2). Motif : une étape dont le caractère aléatoire dépendrait d'un paramètre ferait dépendre du contenu du plan la règle de la graine et `graine_mention`, et appellerait une annotation de l'ADR 0007 pour un cas qu'un `B` petit couvre à coût borné.

7.3. **Appariement** : par clé exacte de cellule (segment, âge ; `annee` hors B13), **sans déduction** ; la modalité `ensemble` s'applique à toutes les cellules ; une table par sexe face à une construction non segmentée par sexe est **refusée** ; une cellule sans valeur de table est un refus (cadre commun de #4). La correspondance entre les modalités du rôle `sexe` des données et `SEXES_TABLE`, et la règle sous `age_atteint_annee` (Q7 (a) : refus), relèvent de la spécification d'`actuary` et de (0'').

7.4. **`annee`** : en B13, la validation n'accepte que des tables **sans** `annee` (refus nommé, sur le modèle de `loi_effective()`, `R/simulation.R:215-218`) ; le sens de `annee` (année calendaire ou génération) n'est pas fixé ici — `tablexp table 1` l'écrit comme un entier quel que soit son sens ; s'il doit être déclaré, ce sera une **métadonnée** (attribut de `table_reference()`, en clair dans la fiche, hors de l'empreinte), fixée par la branche qui lira la première table prospective, par annotation du présent ADR et de l'ADR 0007, point 7.1.

7.5. **`suivre_experience()`** (ADR 0007, point 3.3, réservé ; ADR 0006, point 5) : les statistiques S1 à S12 sont implémentées **une seule fois**, dans le module `validation`, par des fonctions qui reçoivent des cellules (décès, exposition centrale, q̃) et ne connaissent pas l'origine des observations ; l'étape `validation` de `construire_table()` (B13) les appelle sur les cellules de la construction, `suivre_experience()` les appellera plus tard sur de nouvelles observations, avec le **même mode d'entrée** des tables (`tables_reference`, objets `table_reference`) et la **même empreinte**. Sa signature et son rapport figé dédié restent réservés à la branche du suivi.

7.6. **Effet sur les résultats** : aucun par ces règles (grandeurs nouvelles, dans les seules constructions qui déclarent `validation`).

## Options écartées

- **(d) Valeurs de toute table non embarquée écrites dans la fiche** (signalée par `actuary`, non recommandée) : rejeu sans argument nouveau, mais la fiche cesserait d'identifier pour **porter** une entrée — ce que l'ADR 0011, point 5.5, refuse pour les données (« les données sont empreintées telles que reçues ») et que l'ADR 0012, contexte 4, constate (« la fiche ne contient ni exposition ni taux ») ; coût mesuré : 6 758 octets pour une table du moment (60 % d'une fiche de 11 217 octets), 1 561 166 octets pour une table prospective (139 fois la fiche) ; la lisibilité jugée par `actuary` (ADR 0011, point 6.5) serait perdue ; le tiers d'E3.7 « dispose de chaque table importée, comme des données » (annotation du 05/11/2026, (i)) : il n'a pas besoin que la fiche la lui donne ; enfin la table reste de toute façon reçue par `construire_table()`, le point 1 n'étant pas évité.
- **Table (objet `table_reference`) comme valeur d'un paramètre du plan** : le plan est une déclaration canonisée et sérialisée (ADR 0011, points 5 et 6) ; `texte_objet()` refuse un `data.frame` à attributs (mesuré), il faudrait étendre la grammaire du plan ou dépouiller l'objet à la canonisation, `fiche$plan` porterait les valeurs (même coût que (d)), et `valider_plan()`, exportée pour l'application, validerait une donnée. Un plan cite, il ne contient pas.
- **Nom d'une table embarquée dans le plan, chargée par `construire_table()` elle-même** (sans passer par `tables_reference`) : deux formes du même paramètre selon le statut (nom pour une embarquée, clé pour une importée), deux chemins d'entrée à contrôler et à documenter ; avec un accesseur exporté, l'appelant obtient l'objet par son nom et le moteur n'a qu'un mode d'entrée ; le rejeu, lui, relit par nom (M210), sans que le plan change de forme.
- **`donnees` devenant une liste `list(observations = , tables = )`** : écartée pour les mêmes motifs que l'option (B) de l'ADR 0014 (signatures, catalogue des rôles, représentation canonique, contrôle 7 du rejeu, format des jeux simulés) ; une table de référence n'est pas une observation (ADR 0014, point 9).
- **Argument `tables_reference` au rejeu portant aussi les tables embarquées** : contredirait M210 ((f) : relue par son nom) et permettrait de rejouer sous l'étiquette `embarquee` une table que le package n'embarque pas ; la vérification 1.3 à l'entrée de `construire_table()` ferme la même porte en construction.
- **Écart de métadonnées en refus au rejeu** : `nom` et `source` sont du texte libre ; un refus sur un libellé reformulé interdirait un rejeu légitime d'une table ré-importée sous un autre nom de fichier ; le témoin « fiche » le signale sans refuser, ce qui est la règle des témoins (ADR 0012, point 3.6).
- **Copie du `data.frame` nu de la table dans l'objet** (option admise par (h) 4) : redondante avec les valeurs appariées par cellule et avec l'identité dans la fiche ; grossit l'objet et l'empreinte du résultat (48 642 lignes pour une table prospective) sans qu'aucun consommateur (rapport, rejeu) la lise ; exclure le chemin par `CHEMINS_HORS_RESULTAT` reviendrait à stocker ce qu'on n'empreinte pas.
- **Lecture d'une table embarquée par `system.file()` à l'exécution dans `construire_table()` ou `rejouer_fiche()`** : fichier ouvert par le moteur à l'exécution, chemin dépendant de la bibliothèque d'installation (ADR 0011, annotation du 05/11/2026, (c)) ; n'est admis qu'en repli, dans l'accesseur seulement (6.2).
- **`R/sysdata.rda` ou `data/*.rda`** pour les tables embarquées : binaire, non relisible par un certificateur, provenance séparée du contenu ; contraire à « chaque chiffre a sa provenance ».
- **`B = 0` admis (aléa de l'étape dépendant du plan)** : voir 7.2 ; décrite comme alternative si `actuary` établit un coût de Monte-Carlo prohibitif sur une volumétrie réaliste (annotation de l'ADR 0007, point 5.1, et fonction `etape_aleatoire(plan)` à la place de la colonne constante).
- **Champ `tables_reference_mention`** sur le modèle de `provenance_mention` : la ligne `NULL` est sans ambiguïté, le rapport figé porte la phrase lisible ; un champ de plus entrerait dans le même incrément, mais sans consommateur.
- **Racine `table` du texte empreinté** : nom déjà pris par la table finale de l'objet (ADR 0007, point 6.1) ; `table_reference` est le nom de la classe et de l'entrée de `CONTEXT.md`.
- **Tri canonique à l'empreinte seulement, objet gardé dans l'ordre reçu** : deux objets de même contenu et d'ordre différent auraient la même empreinte mais des constructions non `identical` si une étape lisait l'ordre ; le tri dans le constructeur rend l'objet et l'empreinte cohérents (décision A).
